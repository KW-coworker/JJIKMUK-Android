# 로그인·회원가입 API 연동 사전 협의 회의자료

> 작성일: 2026-10-01  
> 검토 대상: Android 현재 구현 + [로그인·회원가입·유저 프로필 API 명세](auth-user-api.md)  
> 검토 브랜치: `feature/auth-api-integration` / 기준 커밋: `7575ca4`  
> 회의 목표: 화면과 서버가 서로 다른 가정을 하는 부분을 정리하고, 연동에 필요한 요청·응답·처리 순서를 확정한다.

> **진행 업데이트:** 회원가입·비밀번호 찾기의 OTP 유효시간을 **5분(300초)**으로 합의하여 프론트 타이머와 미리보기에 반영했다. 기존 재전송 동작도 5분으로 다시 시작한다. **자릿수를 포함한 나머지 질문은 백엔드 검토 회신 대기 중**이며, 아래 선택지는 확정 사항이 아니다. 실제 API 연결 전이므로 서버 동작을 검증한 결과는 아니다.

## 회의 시작 전에 함께 확인할 내용

**로그인·회원가입의 주요 API 9개는 명세에 있다. 다만 현재 화면을 모두 연결하기에는 일부 기능과 데이터 규칙이 부족하다.** API를 처음부터 다시 만들 필요는 없으며, 기존 API로 해결할 부분과 추가·변경할 부분을 구분하는 것이 이번 회의의 목적이다.

핵심 충돌은 실제 연동 전에 합의하는 편이 좋다. 예를 들어 OTP 자릿수가 정해지지 않으면 입력 화면과 검증 코드를 다시 만들 수 있고, 식이조건 저장 방식이 정해지지 않으면 가입은 성공해도 사용자가 선택한 정보가 빠질 수 있다.

다만 모든 부가 기능의 구현이 끝날 때까지 전체 연동을 기다릴 필요는 없다. **기능별로 필요한 계약을 확정한 뒤 이메일 로그인 → 이메일 인증·회원가입 → 비밀번호 찾기 → 사진·Google 로그인 순으로 진행할 수 있다.** 순서는 회의에서 정한 이번 작업 범위에 따라 조정한다.

### 이 자료를 읽는 기준

- **명세에 있음:** 제공된 문서에 적혀 있다는 뜻이다. 실서버 동작을 검증했다는 뜻은 아니다.
- **명세에 없음/불명확:** 백엔드 구현이 없다고 단정하지 않는다. 구현은 되어 있고 문서만 빠졌을 수 있다.
- **현재 앱:** 서버 연결 전의 UI와 임시 검증 로직을 포함한 현재 코드 상태다.
- **제안:** 회의를 위한 선택지다. 합의되기 전에는 서버 계약이나 확정된 제품 정책으로 취급하지 않는다.
- **연결 전 확정:** 해당 기능을 구현하기 전에 답이 필요한 항목이다. 모든 항목이 전체 작업을 막는 것은 아니다.
- **후속 가능:** 이번 범위에서 제외하기로 명시하면 나중에 구현할 수 있다. 화면에 기능이 있다면 미지원 상태가 사용자에게 오해를 주지 않도록 함께 정리한다.

### 회의 진행 순서

1. [지금 사용할 수 있는 API와 공통 기반](#available)을 확인한다.
2. [빠진 기능과 정보](#missing)를 보고 실제 백엔드 구현 여부를 확인한다.
3. [공동 논의 안건](#agenda)을 A01부터 하나씩 검토한다.
4. [제품 결정 사항](#product-decisions)에서 이번에 유지·변경·보류할 UX를 선택한다.
5. [결정 기록표](#decision-log)에 합의 내용, 담당자, 기한을 남긴다.
6. [연동 착수 기준과 검증 항목](#implementation)을 확인하고 작업을 나눈다.

## 1. 지금 사용할 수 있는 API와 공통 기반

여기서 **사용 가능**은 요청·응답 모델과 연결 지점을 준비할 수 있다는 의미다. Base URL이 제공되지 않았으므로 실제 호출 성공을 보장하는 표는 아니다. 각 API의 선행 확인사항도 함께 표시했다.

| 기능 | 현재 명세 | 활용 가능한 부분 | 실제 연결 전 확인할 부분 |
| --- | --- | --- | --- |
| 이메일 로그인 | `POST /api/auth/login` | `email`, `password` 요청과 최상위 `token` 응답 | 서버 주소, 성공 상태, 사용자 ID 획득, 토큰 만료 정책 |
| 이메일 회원가입 | `POST /api/auth/signup` | 기본 계정 필드와 생성된 사용자 ID 응답 | 이메일 인증 증명, 선택 정보 형식, 입력 검증·중복 규칙 |
| 인증번호 전송 | `POST /api/auth/email/send` | 이메일로 코드 발송하는 진입점 | 자릿수, 용도 구분, 가입 이메일 처리, 재전송 정책 |
| 회원가입 인증번호 확인 | `POST /api/auth/email/verify` | `email`, `code`로 검증하고 성공 메시지 반환 | 인증 완료 사실을 최종 가입에 연결하는 방법 |
| 비밀번호 재설정 | `POST /api/auth/password/reset` | `email`, `code`, `newPassword`를 함께 제출 | OTP 자릿수 충돌과 프론트 화면 순서 |
| Google 로그인 | `POST /api/auth/google` | Google `idToken`을 서비스 `token`으로 교환 | Google 설정값, 기존 계정 연결, 신규 사용자 분기 |
| 프로필 조회 | `GET /api/users/{id}` | 본인 정보 조회와 사용자·관리자 권한 구분 | 본인 ID 확보, 응답 nullable 규칙, 비밀번호 해시 반환 여부 |
| 프로필 수정 | `PUT /api/users/{id}` | 기존 프로필 수정 endpoint | 인증, 전체 수정 필드, 생략·삭제 의미, 완전한 응답·오류 |
| 로그인 후 비밀번호 변경 | `PUT /api/users/{id}/password` | 현재 비밀번호와 새 비밀번호를 함께 검증 | 본인 ID, 변경 후 세션, Google 계정의 비밀번호 정책 |

출처: [명세의 API 목록](auth-user-api.md#api-list).

### 1.1 프론트에서 재사용할 수 있는 것

- 로그인·회원가입·비밀번호 찾기의 화면과 이동 경로가 있다.
- 회원가입 입력값은 하나의 `SignUpUiState`에 모인다. 화면마다 별도 가입 요청을 만들 필요는 없다.
- 이메일·비밀번호·닉네임 오류 표시와 OTP 입력 UI가 있다. 서버 오류와 로딩 상태는 추가 연결해야 한다.
- Retrofit, OkHttp, Hilt, DataStore 기반이 있다. 인증 API, 인증 Repository, 세션 저장소는 새로 구현해야 한다.
- 알레르기 26개와 식이조건·채식 유형의 공통 카탈로그가 있다.
- 현재 UI의 상태·화면 분기를 확인하는 단위 테스트가 있다. 실제 API 계약 테스트와 서버 검증은 별도로 필요하다.

### 1.2 문제가 아니므로 불필요하게 바꾸지 않아도 되는 것

| 항목 | 판단 |
| --- | --- |
| 회원가입 응답에 JWT가 없음 | 현재 앱은 가입 완료 후 사용자가 로그인하도록 되어 있어 흐름이 맞는다. 자동 로그인은 별도 제품 선택이다. |
| `{id}`와 `{userId}` 표기 차이 | URL에서 사용자 ID가 들어가는 같은 위치를 뜻한다. 별도 API 충돌이 아니다. |
| API마다 응답 형태가 다름 | 로그인은 `token`, 가입은 숫자 `data`, 조회는 객체 `data`다. API별 응답 모델로 처리하면 된다. |
| 비밀번호 확인 필드가 API에 없음 | 앱에서 입력 일치를 검사한 후 실제 비밀번호만 전송하면 된다. |
| 기저질환·기피 식재료 입력 화면이 없음 | 명세에서 선택 필드이므로 이를 위해 화면을 반드시 추가할 필요는 없다. |
| 재전송 전용 API가 없음 | 동일한 발송 API를 재호출하는 계약이면 충분하다. 동작 규칙 확인이 우선이다. |
| Refresh Token이 없음 | JWT 만료 시 재로그인하는 정책도 가능하다. 갱신 기능을 제공할 때 추가 계약이 필요하다. |

## 2. 빠진 기능과 정보

### 2.1 추가 API 또는 기존 API 확장이 필요한 후보

**새 endpoint가 무조건 필요하다는 목록은 아니다.** 기존 응답 필드 추가, 기존 API의 동작 명시, UX 변경으로 해결할 수 있는 항목을 구분했다.

| ID | 부족한 기능 | 현재 화면에서 필요한 이유 | 가능한 해결 방식 | 관련 안건 |
| --- | --- | --- | --- | --- |
| M01 | 닉네임 사전 중복 확인 | 닉네임 입력 단계에서 이미 사용 중이라는 오류를 보여준다. | 고유 닉네임 정책이라면 확인 API 제공, 최종 가입에서만 검사하도록 UX 변경, 또는 중복 허용 정책 확정 | A06 |
| M02 | 프로필 사진 업로드·조회 | 가입 마지막 화면에서 사진을 고를 수 있다. | 가입 API의 업로드 지원 또는 별도 업로드 API와 이미지 연결 필드. 조회 응답에도 이미지 정보 필요 | A07 |
| M03 | 로그인한 본인 ID 확보 | 프로필 조회·수정·비밀번호 변경에 ID가 필요하다. | 로그인 응답에 ID 추가, 본인 조회 API 제공, 또는 공식 JWT claim 계약 | A08 |
| M04 | 재설정용 OTP 사전 검증 | 현재 앱은 OTP를 검증한 다음 새 비밀번호를 입력한다. | 단계별 UX 유지 시 검증·재설정 증명 계약 추가. 최종 일괄 검증 UX로 바꾸면 추가 API 불필요 | A03 |
| M05 | 모든 식이조건의 저장·복원 | 저당·저염·고단백 등 여러 조건과 채식 유형을 저장해야 한다. | 기존 가입·조회·수정 API의 허용 값과 필드 확정, 필요하면 필드 확장 | A05 |
| M06 | 토큰 갱신 | 만료 후에도 사용자가 다시 로그인하지 않게 하려면 필요하다. | 갱신 정책과 API 추가. 만료 시 재로그인 정책이면 추가 불필요 | A09 |
| M07 | 서버 로그아웃·토큰 폐기 | 로그아웃한 토큰을 서버에서도 즉시 무효화하려면 필요하다. | 서버 폐기 기능 제공. 기기에서 토큰만 삭제하는 정책이면 별도 API 없이 가능 | A09 |
| M08 | Google 신규 사용자 분기 정보 | 첫 로그인 사용자에게 추가 프로필 입력을 안내하려면 필요하다. | 로그인/프로필 응답에 판단 기준 제공. 항상 홈으로 이동하는 정책이면 별도 분기 정보가 필수는 아님 | A10 |

### 2.2 API 추가보다 문서 보완이 먼저인 정보

- 개발 서버 주소와 일반 사용자 테스트 환경
- OTP 자릿수·유효시간·재전송 제한·코드 소비 규칙
- 가입 시 이메일 인증 완료 여부를 서버가 확인하는 방법
- 비밀번호·닉네임·이메일의 검증 규칙
- 알레르기·식이조건의 허용 값과 복수 값 표현 방식
- 선택값을 보내지 않거나 전부 지울 때의 의미
- API별 성공 HTTP 상태와 오류 응답
- JWT 만료 시간과 만료·권한 부족 오류 구분
- 프로필 수정의 인증 조건과 전체 요청·응답
- Google 로그인 환경 설정과 기존 계정 연결 정책

## 3. 프론트·백엔드 공동 논의 안건

각 안건의 질문에 답한 뒤 [결정 기록표](#decision-log)에 결과를 남긴다. 백엔드 실제 동작을 먼저 확인하고, 현재 구현과 달라야 한다면 어느 쪽을 변경할지 정한다.

<a id="a01"></a>
### A01. 서버 주소와 테스트 준비

**우선순위: 첫 실제 호출 전에 확정 / 논의: 백엔드 중심, 프론트 확인**

**현재 상태**

- 명세에는 Base URL이 없다.
- 앱의 백엔드 주소는 `http://10.0.2.2:8080/`으로 고정되어 있다. Android 에뮬레이터에서 개발 PC의 서버로 접근하기 위한 현재 설정이며, 실제 팀 개발 서버 주소가 아니다.
- 명세에는 관리자 테스트 계정이 있지만 일반 사용자 테스트도 필요하다. 관리자만으로 확인하면 본인 정보 접근 권한 문제를 놓칠 수 있다.

**회의 질문**

- 개발 서버 주소, HTTP/HTTPS 여부, 접속에 필요한 네트워크 조건은 무엇인가?
- 에뮬레이터와 실기기에서 모두 접근 가능한가?
- 현재 서버 버전이 이 명세와 일치하는가?
- 실제 메일을 받을 수 있는 테스트 이메일과 일반 사용자 계정은 어떻게 준비하는가?
- OTP 재발송 제한과 가입 테스트 데이터 정리 방식은 무엇인가?

**회의 산출물:** 개발 Base URL, 테스트 방법, 일반 계정 준비 담당자. 계정 비밀번호·실제 JWT는 이 회의록에 추가하지 않고 팀의 별도 공유 경로를 사용한다.

근거: [명세 공통 규칙](auth-user-api.md#common-rules), [NetworkModule](../app/src/main/java/com/coworker/jjikmuk/di/NetworkModule.kt).

<a id="a02"></a>
### A02. OTP 자릿수·시간·발송·재전송

**우선순위: 이메일 인증 연결 전 확정 / 논의: 공동**

| 구분 | 현재 앱 | 명세 |
| --- | --- | --- |
| 회원가입 OTP | 4자리 | 발송·검증 6자리 |
| 비밀번호 찾기 OTP | 4자리 | 공통 발송 6자리, 재설정 설명 4자리 |
| 유효시간 | **5분, 300초로 변경 완료** | **5분으로 합의** |
| 발송 용도 | 회원가입과 비밀번호 찾기를 화면에서 구분 | `/email/send` 요청에는 `email`만 있음 |
| 재전송 | 로컬 테스트 번호와 타이머를 즉시 교체 | 제한·기존 코드 처리·실패 동작 미기재 |

**왜 합의가 필요한가?**

6자리 코드가 도착해도 현재 앱은 4자리까지만 입력받는다. 기존 3분 타이머와 명세의 5분 차이는 합의대로 수정했다. 자릿수와 가입·재설정이 같은 이메일로 코드를 요청했을 때 서로 영향을 주는지는 아직 확인이 필요하다.

**회의 질문**

1. 실제 발송 코드는 회원가입과 재설정 각각 몇 자리인가? 6자리로 통일할 것인가?
2. 유효시간은 **5분으로 합의 완료**. 서버 발급 시점·만료 시각 또는 남은 시간을 응답할 수 있는가는 계속 확인한다.
3. 이미 가입된 이메일로 회원가입 코드를 요청하면 어떻게 응답하는가?
4. 미가입 이메일로 재설정 코드를 요청하면 어떻게 응답하는가? 현재 앱은 발송 단계에서 미가입 오류를 보여주지만, 명세에는 최종 재설정의 404만 있다.
5. 용도 구분 없이 같은 API를 사용할 수 있는가? 필요하면 요청 필드 또는 endpoint를 변경할 것인가?
6. 재전송은 같은 `/email/send` 재호출인가? 대기시간·횟수 제한·제한 시 응답은 무엇인가?
7. 재전송 성공 시 이전 코드는 무효화되는가? 재전송 실패 시 기존 코드는 유지되는가?
8. 검증 실패 횟수 제한과 코드 만료·미요청 상태의 처리 규칙은 무엇인가?

**반영 완료:** 회원가입·비밀번호 찾기 타이머와 공통 화면 미리보기를 5분으로 변경하고 기존 테스트의 시간 기대값을 수정했다.

**추가 합의 후 프론트 작업:** 자릿수가 확정되면 입력칸 수, ViewModel 입력 제한, 완료 조건, 안내 문구, 테스트를 함께 수정한다. 실제 API 연결 시에는 발송 성공 이후에 다음 화면으로 이동하고 재전송 성공 이후에 안내·타이머를 갱신한다. 서버 만료 판정이 최종 기준이다.

근거: [코드 발송 명세](auth-user-api.md#send-email-code), [코드 검증 명세](auth-user-api.md#verify-email-code), [OTP 공통 화면](../app/src/main/java/com/coworker/jjikmuk/feature/auth/presentation/common/AuthOtpScreen.kt), [OTP 입력 컴포넌트](../app/src/main/java/com/coworker/jjikmuk/ui/component/JjikmukOtpTextField.kt).

### A03. 비밀번호 찾기 화면 순서와 코드 소비

**우선순위: 비밀번호 찾기 연결 전 확정 / 논의: 공동·제품 결정 필요**

현재 앱은 `이메일 → OTP 검증 성공 → 새 비밀번호 → 완료` 순서다. API는 `/password/reset`에 `email`, `code`, `newPassword`를 한 번에 보내야 실제 검증과 변경을 수행한다.

또한 명세에 따르면 `/email/verify`는 성공 시 임시 인증 데이터를 즉시 삭제한다. **재설정 OTP 화면에 이 API를 먼저 붙이면 최종 재설정에서 사용할 코드가 사라질 수 있다.** 명세에 없는 코드 재사용을 가정하면 안 된다.

| 선택 | 처리 흐름 | 필요한 변경 |
| --- | --- | --- |
| A. 기존 재설정 API 유지 | OTP 화면은 코드 입력만 받음 → 새 비밀번호 입력 → `/password/reset`에서 함께 검증 | OTP 화면을 인증 성공으로 처리하지 않는다. 최종 코드 오류와 재입력·재전송 경로를 추가한다. |
| B. 현재 단계별 검증 유지 | OTP 단계에서 서버 검증 → 재설정 권한을 증명하는 값/상태 확보 → 새 비밀번호 제출 | 재설정용 검증 계약과 최종 재설정 계약을 함께 추가·변경한다. 기존 회원가입 검증 API를 그대로 재사용하지 않는다. |

**제안:** 기존 API를 유지하려면 A가 맞다. OTP 단계에서 실제 검증 성공을 보여주는 UX가 중요하다면 B를 선택한다. 단순히 앱에서 코드 길이만 확인하고 ‘인증 성공’으로 표시하는 것은 A의 올바른 구현이 아니다.

**추가로 결정할 내용**

- A에서 새 비밀번호를 입력하는 동안 코드가 만료되면 어느 화면에서 재전송하는가?
- 현재 앱은 OTP 성공 시 타이머를 멈추고 OTP 화면을 뒤로가기 스택에서 제거한다. 변경된 흐름에 맞게 이를 어떻게 조정하는가?
- 코드 오류·만료와 새 비밀번호 정책 오류를 각각 어디에 표시하는가?
- 미가입 이메일은 발송 시점과 최종 재설정 중 어느 시점에 안내하는가?
- 성공 후 로그인 화면으로 돌아가는 현재 흐름을 유지하는가?

근거: [비밀번호 재설정 명세](auth-user-api.md#reset-password), [PasswordResetViewModel](../app/src/main/java/com/coworker/jjikmuk/feature/auth/presentation/passwordreset/PasswordResetViewModel.kt), [인증 화면 이동](../app/src/main/java/com/coworker/jjikmuk/feature/auth/navigation/AuthNavHost.kt).

### A04. 이메일 인증 완료와 최종 회원가입의 연결

**우선순위: 실제 회원가입 연결 전 확정 / 논의: 백엔드 중심, 프론트 상태 처리 협의**

**명세에 함께 적힌 내용**

- `/email/verify` 성공 시 인증 데이터를 즉시 삭제한다.
- 응답은 성공 메시지뿐이다.
- `/signup`에는 인증번호나 인증 완료 증명 필드가 없다.

서버가 별도 인증 완료 상태를 저장할 수 있으므로, 문서만 보고 서버 검증이 없다고 단정하지 않는다. 다만 앱의 `isOtpVerified = true`만으로 가입 권한을 증명할 수는 없다. **서버가 최종 가입 때 인증된 이메일인지 확인하는 규칙이 필요하다.**

**회의 질문**

1. 코드 삭제 후에도 인증 완료 상태를 서버가 별도로 보관하는가?
2. 인증 완료 상태로 관리하는 방식인가, 앱에 증명 토큰을 반환하는 방식인가?
3. 인증 완료 후 가입 가능한 시간은 얼마인가? OTP 자체의 5분과 같은 개념인가?
4. 이메일 변경·재전송·가입 성공 시 인증 상태는 어떻게 처리되는가?
5. 가입 실패 후 재시도할 때 인증을 다시 해야 하는가?
6. 가입 요청의 응답을 받지 못했지만 서버에서는 가입된 경우, 재시도 결과와 사용자 안내는 어떻게 처리하는가?

현재 앱은 인증 이후 비밀번호·닉네임·조건·사진을 입력하므로 시간이 더 걸릴 수 있다. ‘인증 완료 후 가입 가능 시간’과 ‘메일 코드 유효시간’을 구분해 명세에 적어야 한다.

### A05. 알레르기·식이조건·채식 유형의 저장 형식

**우선순위: 선택 정보를 포함한 회원가입 연결 전 확정 / 논의: 공동**

| 현재 프론트 입력 | 앱 내부 표현 | 명세의 대응 | 결정할 내용 |
| --- | --- | --- | --- |
| 알레르기 복수 선택 | `egg`, `milk`, `wheat` 등 영문 ID 집합 | `allergies: String`, 예시 `"땅콩, 밀"` | ID/표시 이름, String/배열, 구분자·공백 규칙 |
| 저당·저염·글루텐프리·저칼로리·저지방·고단백 | 여러 `SignUpCondition` 선택 | 명확한 전용 필드 없음 | `specialDiet`에 포함하는지, 별도 필드가 필요한지 |
| 채식 세부유형 | 비건·락토·오보·락토오보·페스코·폴로 중 하나 | `specialDiet: String`, 예시 비건·할랄 | 6개 유형 지원과 다른 식이조건과의 조합 형식 |
| 기저질환 입력 없음 | 없음 | 선택 필드 `diseases` | 이번 가입에서는 생략 가능한지 |
| 기피 식재료 입력 없음 | 없음 | 선택 필드 `dislikedIngredients` | 이번 가입에서는 생략 가능한지 |

**기존 합의와의 차이**

[공통 카탈로그](food-preference-catalog.md)는 백엔드와 맞춘 알레르기 26개와 영문 ID를 기준으로 한다. 새 명세는 한글 문자열 예시를 사용한다. DB가 영문 ID를 쓴다는 사실만으로 API도 같은 형식이라고 단정할 수 없으므로 API 경계의 규칙을 확인한다.

**회의에서 실제 예시로 확정할 내용**

사용자가 다음을 선택한 경우를 기준으로 가입 요청과 조회 응답의 완전한 JSON을 작성한다.

- 알레르기: 계란 + 밀
- 식이조건: 저당 + 고단백
- 채식 유형: 락토오보
- 기저질환·기피 식재료: 미입력

이어서 ‘아무 조건도 선택하지 않은 가입’과 ‘기존 조건을 모두 해제하는 수정’ 예시도 각각 작성한다. 세 예시가 있으면 저장·조회·수정이 같은 의미로 연결되는지 확인하기 쉽다.

**주의할 해석**

- 현재 명세 타입은 String이다. 합의 없이 배열로 보내지 않는다.
- `SignUpCondition.Allergy`와 `Vegetarian`은 세부 화면을 여는 상위 선택값이다. 이를 그대로 서버 식단값으로 보낼 필요가 있는지 별도 합의한다.
- 저당을 선택했다고 `diseases: "당뇨"`를 보내면 안 된다. 선호와 질환은 다른 정보다.
- ‘할랄’은 명세의 예시다. 그것만으로 프론트 선택지에 추가하지 않는다.
- 이름과 아이콘은 화면 표시용이다. 서버 계약과 별개로 이모지를 전송할 필요는 없다.
- 알레르기 26개 전체의 허용 ID와 채식 6개·식이조건 6개의 지원 여부를 확인한다.

**회의 산출물:** 필드별 타입·허용 값·복수 값 결합 규칙·미입력 표현·전체 해제 표현·조회 응답 복원 규칙. 알 수 없는 값이나 구형 저장값을 받는 경우의 처리도 정한다.

근거: [가입 요청 필드](auth-user-api.md#signup), [공통 카탈로그](food-preference-catalog.md), [프로필 선택 항목 표시](../app/src/main/java/com/coworker/jjikmuk/feature/auth/presentation/signup/SignUpProfileScreen.kt).

### A06. 닉네임 중복과 입력값 검증

**우선순위: 회원가입 연결 전 확정 / 논의: 공동·제품 결정 필요**

현재 닉네임 단계는 임시 데이터로 중복 오류를 보여준다. API 명세에는 중복 확인 endpoint와 최종 가입의 닉네임 중복 오류가 없다. **먼저 닉네임을 고유하게 관리하는지부터 확인해야 한다.**

| 선택 | 사용자 경험 | 서버 요구사항 |
| --- | --- | --- |
| 중복 허용 | 같은 닉네임을 사용해도 가입 가능 | 중복 허용 명시, 프론트의 중복 오류 흐름 제거 |
| 사전 확인 + 최종 검사 | 닉네임 단계에서 먼저 안내 | 사전 확인 기능과 최종 가입 시 중복 검사 |
| 최종 가입에서만 검사 | 마지막에 중복 안내를 받을 수 있음 | 가입 오류 계약과 프론트 수정·재시도 흐름 |

프로필 확인 화면에서도 닉네임을 다시 수정할 수 있다. 앞 단계의 확인 결과를 그대로 믿으면 안 된다. 이름을 바꾸면 확인 상태를 초기화해야 하고, 사전 확인 후 다른 사용자가 먼저 등록할 수도 있으므로 최종 서버 검사는 별개다.

**함께 확정할 입력 정책**

| 필드 | 현재 앱 | 백엔드에서 확인할 규칙 |
| --- | --- | --- |
| 비밀번호 | 6자 이상, 확인 입력과 일치 | 최소·최대 길이, 문자 조합·공백·허용 문자, 정확한 오류 |
| 닉네임 | 공백 여부와 임시 중복 검사 | 최소·최대 길이, 허용 문자, 앞뒤 공백, 대소문자·중복 판정 |
| 이메일 | 형식 검사, 일부 검증에서 앞뒤 공백 제거 | 저장·비교 시 공백·대소문자 처리, 중복 판정 |

명세에서 비밀번호는 필수지만 누락 오류 예시에는 이메일·닉네임만 있다. 비밀번호가 선택값이라는 뜻은 아니므로 비밀번호 누락 시 응답을 보완한다.

**제안:** 고유 닉네임 정책이라면 현재 UX에 맞게 사전 확인을 제공하고, 최종 가입 실패도 프로필 화면에서 수정할 수 있게 한다. 비밀번호 확인값은 서버에 새 필드를 추가하지 않고 앱에서 검사한다.

근거: [SignUpViewModel](../app/src/main/java/com/coworker/jjikmuk/feature/auth/presentation/signup/SignUpViewModel.kt), [비밀번호 검증](../app/src/main/java/com/coworker/jjikmuk/feature/auth/presentation/common/AuthPasswordValidation.kt), [프로필 화면](../app/src/main/java/com/coworker/jjikmuk/feature/auth/presentation/signup/SignUpProfileScreen.kt).

<a id="a07"></a>
### A07. 프로필 사진을 언제, 어떻게 저장할 것인가?

**우선순위: 사진 기능을 이번에 유지하면 선행 확정 / 논의: 공동·범위 결정 필요**

현재 가입 화면에서 갤러리 사진 또는 카메라 미리보기를 선택할 수 있다. 앱 상태에는 로컬 URI 또는 Bitmap이 들어간다. API 명세의 가입·조회·수정에는 사진 필드가 없다.

로컬 URI를 JSON에 넣는 것으로 사진 업로드가 되지는 않는다. 다른 기기나 재로그인 시 복원하려면 서버가 저장한 이미지 식별값 또는 URL이 필요하다.

**회의 질문**

1. 사진을 이번 가입 연동에 포함하는가, 후속 작업으로 미루는가?
2. 가입 요청에 파일을 함께 보내는가, 별도 업로드 후 식별값을 보내는가, 로그인 후 업로드하는가?
3. 업로드에 서비스 JWT가 필요한가? 현재 가입 응답에는 JWT가 없으므로 가입 직후 인증 업로드를 바로 호출할 수 있다는 가정은 하면 안 된다.
4. 파일 필드명·형식·크기 제한·반환값은 무엇인가?
5. 프로필 조회에서 어떤 이미지 정보를 반환하는가? URL 만료가 있다면 어떻게 갱신하는가?
6. 사진 교체·삭제·기본 이미지 복원은 어떻게 요청하는가?
7. 가입 성공 후 사진 업로드만 실패하면 가입 성공으로 처리하고 재시도하는가?

카메라는 현재 `TakePicturePreview()` 결과를 사용한다. 업로드 이미지 품질 요구가 있다면 원본 촬영 방식 변경 여부도 함께 확인한다.

**제안:** 현재 화면을 완성하는 범위라면 사진 저장까지 포함한다. 미룬다면 사진 선택 UI도 함께 조정해 서버에 저장되지 않는 사진을 가입 완료 정보처럼 보여주지 않는다.

근거: [프로필 사진 선택 코드](../app/src/main/java/com/coworker/jjikmuk/feature/auth/presentation/signup/SignUpProfileScreen.kt), [가입 명세](auth-user-api.md#signup).

<a id="a08"></a>
### A08. 로그인 후 본인 사용자 ID 확보

**우선순위: 로그인 후 프로필 연결 전 확정 / 논의: 백엔드 중심**

이메일·Google 로그인 응답에는 `token`만 있고, 프로필 API에는 `{id}`가 필요하다. 가입 응답의 ID를 기기에 저장하는 방법만으로는 다른 기기나 재설치 후 기존 계정 로그인에 대응할 수 없다.

| 선택 | 방식 | 확인할 내용 |
| --- | --- | --- |
| 로그인 응답 확장 | 서비스 토큰과 사용자 ID를 함께 반환 | 이메일·Google 로그인 모두 같은 ID 계약을 제공하는가? |
| 본인 조회 API | 토큰으로 본인 정보를 조회 | 정확한 URL·응답·오류는 무엇인가? |
| 공식 JWT claim | 문서화된 claim에서 ID를 읽음 | claim 이름·타입·존재 보장. 앱의 디코딩을 서버 권한 검증의 대체로 사용하지 않음 |

**제안:** 이메일·Google 로그인에서 공통으로 사용할 명시적 ID 제공 방식을 정한다. 예시 JWT의 내용만 보고 ID 위치를 추측하지 않는다. 본인 확인과 접근 권한은 계속 서버가 검증한다.

상품 API에도 선택적 `userId` 파라미터가 있지만 현재 Repository는 전달하지 않는다. 인증 후 맞춤 분석에 ID가 필요한지, 서버가 토큰에서 사용자를 식별하는지도 별도로 확인한다.

근거: [로그인 명세](auth-user-api.md#login), [프로필 조회 명세](auth-user-api.md#get-user), [ProductApi](../app/src/main/java/com/coworker/jjikmuk/data/remote/api/ProductApi.kt), [ProductRepositoryImpl](../app/src/main/java/com/coworker/jjikmuk/data/repository/ProductRepositoryImpl.kt).

<a id="a09"></a>
### A09. 로그인 유지·토큰 만료·로그아웃

**우선순위: 로그인 세션 구현 전 확정 / 논의: 공동·제품 결정 필요**

명세에는 서비스 JWT 하나만 있다. Refresh Token, 갱신 API, 로그아웃 API, 만료 시간은 없다. **이 자료는 Refresh Token이 존재한다고 가정하지 않는다.**

| 결정 | 선택지 | 설명 |
| --- | --- | --- |
| JWT 만료 후 | 재로그인 / 갱신 후 유지 | 갱신을 선택할 때만 갱신 수단·API·실패 처리가 추가로 필요 |
| 로그아웃 | 기기의 토큰 삭제 / 서버에서도 토큰 폐기 | 로컬 삭제만으로 서버 토큰 자체가 무효화되지는 않음 |
| 비밀번호 변경·재설정 후 | 기존 세션 유지 / 일부 또는 전체 무효화 | 현재 기기와 다른 기기의 처리를 구분해 합의 |
| 앱 재실행 | 저장된 세션 확인 후 홈 / 로그인 안내 | 만료·무효 상태와 네트워크 실패를 구분해야 함 |

**회의 질문**

- JWT 유효기간과 만료를 확인할 방법은 무엇인가?
- 토큰이 없거나 만료·변조된 경우 각각 어떤 상태·오류를 반환하는가?
- 본인 외 사용자에 접근한 권한 부족과 세션 만료를 어떻게 구분하는가?
- 갱신을 지원하면 요청·응답, 토큰 교체, 재사용·실패 정책은 무엇인가?
- 로그아웃 버튼과 세션 만료 안내를 이번 프론트 범위에 포함하는가?

프로필 조회 명세는 미로그인도 403으로 설명한다. 따라서 앱이 모든 403을 세션 만료로 처리하면 정상 로그인 사용자의 권한 부족도 로그아웃으로 처리할 수 있다. 명확한 오류 구분이 필요하다.

근거: [인증 공통 규칙](auth-user-api.md#common-rules), [조회 오류](auth-user-api.md#get-user), [비밀번호 변경](auth-user-api.md#change-password).

<a id="a10"></a>
### A10. Google 로그인·자동 가입·추가 프로필 입력

**우선순위: Google 연동을 이번에 포함하면 선행 확정 / 논의: 공동·제품 결정 필요**

명세는 첫 Google 로그인에서 임시 닉네임으로 자동 가입하고 서비스 JWT를 반환한다. 응답에는 사용자 ID, 신규 가입 여부, 프로필 입력 완료 여부가 없다. 현재 앱의 Google 버튼은 실제 인증 없이 홈으로 이동하는 임시 동작이다.

**회의 질문**

1. 이번 연동 범위에 Google 로그인을 포함하는가?
2. 처음 가입된 사용자는 홈으로 바로 이동하는가, 추가 프로필 입력 화면으로 이동하는가?
3. 추가 입력이 있다면 신규/미완료 판단 기준을 어떤 응답으로 제공하는가?
4. 일반 가입과 같은 이메일의 Google 계정이면 연결·거절·별도 안내 중 무엇을 하는가?
5. Google 가입자는 이메일·비밀번호 로그인, 비밀번호 찾기·변경을 사용할 수 있는가?
6. 추가 정보 저장에 프로필 수정 API를 사용할 수 있는가? 식이조건·사진까지 지원하는가?
7. 사용할 Google Client ID, 서버가 검증하는 대상 Client ID, Android 패키지·서명 등록 정보는 준비되어 있는가?

**판단 시 주의:** 알레르기·식이조건이 비어 있다는 것만으로 프로필 미완료를 판단하지 않는다. 현재 일반 가입에서도 조건 미선택은 정상 완료 상태다.

Google에서 받은 `idToken`과 서버가 발급한 서비스 `token`은 다른 값이다. 서비스 API에는 서버가 발급한 토큰을 사용한다. 일반 가입의 이메일·OTP 단계를 Google 사용자에게 그대로 반복시키는지도 별도 결정 없이 가정하지 않는다.

근거: [Google 로그인 명세](auth-user-api.md#google-login), [인증 화면 이동](../app/src/main/java/com/coworker/jjikmuk/feature/auth/navigation/AuthNavHost.kt).

<a id="a11"></a>
### A11. 프로필 조회·수정의 완전한 계약

**우선순위: 프로필 저장·복원 연결 전 확정 / 논의: 백엔드 중심, 프론트 사용 범위 확인**

현재 `PUT /api/users/{id}`에는 일부 요청 예시와 개략 응답만 있다. 인증 조건, 전체 수정 필드, 생략한 필드 처리도 명확하지 않다.

**회의 질문**

- 수정 가능한 필드 전체는 무엇인가? `specialDiet`, `dislikedIngredients`, 추가 식이조건·사진을 포함하는가?
- 필드를 생략하면 기존 값 유지인가, 초기화인가?
- `null`, `""`, `"없음"`의 의미는 같은가? 전체 조건 해제를 어떻게 표현하는가?
- 본인과 관리자 각각 어떤 수정이 가능한가?
- 이메일 변경에 중복 검사·재인증이 필요한가? 변경 후 토큰과 로그인 ID는 어떻게 되는가?
- 수정 성공 시 전체 프로필을 반환하는가? 실제 JSON과 모든 오류는 무엇인가?
- 조회 응답의 선택 필드는 `null`, 빈 값, 필드 생략 중 무엇이 가능한가?

**비밀번호 해시 반환 확인:** 조회 예시에 `data.password` 해시가 포함되어 있다. 실제 서버에서도 반환한다면 서버 응답에서 제외하도록 요청한다. 프론트에서 화면에 숨기는 것만으로 응답에 포함된 문제가 해결되지는 않으며, 앱에서 비밀번호 비교에 사용하지 않는다.

**임시 비밀번호 표현 확인:** 로그인 후 변경 API에는 ‘이메일로 받은 임시 비밀번호’가 등장하지만 발급 API는 없다. 이전 설명의 잔재인지 실제 기능인지 확인한다. 현재 `/password/reset`이 임시 비밀번호를 발급한다고 해석하지 않는다.

근거: [프로필 조회](auth-user-api.md#get-user), [프로필 수정](auth-user-api.md#update-user), [로그인 상태의 비밀번호 변경](auth-user-api.md#change-password).

<a id="a12"></a>
### A12. 성공·오류 응답을 화면과 연결하는 규칙

**우선순위: 각 기능 연결 전 필요한 오류부터 확정 / 논의: 공동**

가입·이메일 로그인·프로필 조회·수정은 성공 HTTP 상태가 미기재다. 발송·프로필 수정에는 오류 예시가 없고, 재설정의 잘못된 코드·만료 오류 본문도 빠져 있다.

**왜 필요한가?**

같은 400이라도 코드가 틀리면 재입력, 만료면 재전송, 닉네임 중복이면 이름 수정이 필요하다. 앱이 어떤 상태와 응답 필드를 기준으로 구분할지 정해야 한다.

| 응답 종류 | 백엔드 확인 | 프론트 처리 방향 |
| --- | --- | --- |
| 성공 | 실제 HTTP 상태, 필수 응답값, nullable 규칙 | 메시지 문자열 일치가 아닌 응답 계약으로 성공 판정 |
| 입력 오류 | 필드별 오류와 식별 가능한 코드 여부 | 해당 입력란 또는 최종 제출 화면에 표시 |
| OTP 오류 | 불일치·만료·미요청·횟수 제한 구분 | 재입력/재전송 경로 제공 |
| 인증·권한 오류 | 로그인 실패·토큰 만료·접근 권한 부족 구분 | 잘못된 계정 안내와 세션 종료를 구분 |
| 서버/네트워크 실패 | 서버 오류 형식, 재요청 시 처리 | 입력 유지, 로딩 해제, 중복 요청 없이 재시도 |

**제안:** 오류 `message`와 별개로 안정적인 오류 식별 코드를 제공하면 문구 변경과 화면 동작을 분리할 수 있다. 기존 오류 본문에는 `status`, `message`만 있으므로 새 코드가 있다고 가정하지 않는다. 지원하지 않으면 실제로 사용할 구분 규칙을 명세에 적는다.

응답 형식을 모든 API에서 통일하는 것은 이번 연동의 필수 조건은 아니다. 다만 각 API의 실제 형태는 확정되어야 한다.

근거: [공통 오류 형식](auth-user-api.md#common-rules), [원문 확인사항 Q9](auth-user-api.md#open-questions).

<a id="a13"></a>
### A13. 로그인 이후 화면·로컬 데이터까지 어디까지 연결할 것인가?

**우선순위: 이번 완료 범위 결정 / 논의: 프론트 중심, 관련 API는 공동 확인**

로그인 성공 후 홈으로 이동하는 것과, 실제 계정 정보가 앱 전체에 반영되는 것은 다른 작업이다. 이번 완료 기준을 분명히 정한다.

| 현재 상태 | 연결 시 필요한 작업 | 범위 제안 |
| --- | --- | --- |
| 마이페이지 이름·이메일이 고정값 | 본인 조회 결과 표시 | 본인 프로필 연결에 포함 |
| 가족 식이조건의 ‘나’가 로컬 예시 데이터 | 가입한 본인의 조건과 연결, 기존 로컬 데이터 처리 | 본인 데이터 반영과 계정 구분은 함께 검토 |
| 가족 프로필은 한글 값과 로컬 ID를 사용 | 공통 ID·서버 프로필과의 매핑 필요 | 가족 전체 서버 연동은 별도 범위 가능 |
| 로컬 가족 데이터에 소유 사용자 ID가 없음 | 계정 전환 시 데이터 구분·초기화 정책 | 로그인 상태를 실제 사용하기 전에 결정 |
| 상품 API의 `userId`를 현재 호출에서 생략 | 토큰/ID 중 서버가 어떤 방식으로 개인화하는지 확인 | 인증 연결 후 맞춤 결과를 완료 기준에 넣는다면 포함 |

가족 프로필 전체 API나 계정 삭제 API는 이번 로그인·회원가입 필수 누락으로 단정하지 않는다. 이번 기능 범위에 포함하기로 결정한 경우 별도 명세를 요청한다.

근거: [마이페이지](../app/src/main/java/com/coworker/jjikmuk/feature/mypage/presentation/MyPageScreen.kt), [로컬 가족 프로필 저장소](../app/src/main/java/com/coworker/jjikmuk/data/repository/FamilyProfileRepositoryImpl.kt), [가족 프로필 Entity](../app/src/main/java/com/coworker/jjikmuk/data/local/entity/FamilyProfileEntity.kt).

## 4. 제품·화면 관점에서 선택할 사항

백엔드 실제 동작 확인과 별개로, 사용자 경험이나 이번 작업 범위를 정해야 하는 목록이다. 제안은 확정 사항이 아니다.

| 항목 | 선택지 | 검토 제안 | 관련 안건 |
| --- | --- | --- | --- |

## 6. 회의 후 연동 착수 기준과 작업 순서

### 6.1 기능별 착수 기준

전체 안건의 구현 완료를 기다리는 대신, 해당 기능의 계약이 합의되었는지 확인한다. 합의된 응답으로 앱 측 개발을 진행할 수 있지만, 실서버 연결 완료 판단은 실제 호출 검증 후에 한다.

| 단계 | 선행 합의 | 완료로 볼 기준 |
| --- | --- | --- |
| 1. 이메일 로그인·세션 | A01, A08, A09, 로그인 관련 A12 | 실제 로그인, 토큰 처리, 재실행·만료·실패 처리 |
| 2. 이메일 인증·회원가입 | A02, A04, A05, A06, 관련 A12, 사진 범위 A07 | 실제 메일 인증 후 가입, 선택 정보 저장, 실패 시 입력 유지·재시도 |
| 3. 비밀번호 찾기 | A02, A03, A06, A09의 변경 후 세션 정책, 관련 A12 | 확정된 순서로 변경하고 새 비밀번호로 로그인 |
| 4. 본인 프로필 반영 | A05, A08, A11, A13 | 조회값이 화면과 선택 상태에 복원되고 계정 전환 시 데이터가 섞이지 않음 |
| 5. 사진·Google 기능 | A07, A10 및 관련 앞 단계 | 업로드·추가 정보·신규/기존 사용자 흐름까지 검증 |

사진이 최종 가입 요청에 포함되는 설계를 선택하면 사진 작업을 2단계와 함께 진행한다. Google을 후속으로 미루면 이메일 로그인·가입은 먼저 진행할 수 있다.

### 6.2 프론트가 처리할 구현 작업

아래는 백엔드에 새 API를 요구하는 항목이 아니라, 합의된 API를 앱에 연결하는 작업이다.

1. 인증 API와 요청·응답 DTO, Repository, Hilt 주입 구조를 만든다.
2. 로컬 고정 계정·OTP·닉네임 검증을 실제 서버 호출로 교체한다.
3. 가입·비밀번호 재설정은 서버 성공 응답 이후에만 완료 화면으로 이동한다.
4. 로딩, 연속 클릭 방지, 서버 오류, 네트워크 실패와 재시도를 처리한다.
5. 요청 중 이메일·닉네임이 바뀌거나 뒤로 이동한 경우 이전 요청 결과가 새 입력을 인증하지 않도록 처리한다.
6. 합의된 세션 저장·복원·만료·로그아웃 방식을 연결한다. 갱신은 서버가 지원할 때 구현한다.
7. 실제 인증 요청을 보내기 전에 현재의 `BODY` 로그가 비밀번호·OTP·토큰 본문을 기록하지 않도록 바꾼다. 단순히 Authorization 헤더만 가리는 것으로는 본문 기록이 해결되지 않는다.
8. 백엔드와 AI 서버가 공유하는 OkHttp 설정에서 서비스 토큰의 전송 대상을 구분한다.
9. 합의된 범위의 본인 프로필, 마이페이지, 맞춤 정보와 로컬 데이터 처리를 연결한다.
10. 명세에 맞춘 단위 테스트와 실제 서버·에뮬레이터 검증을 수행한다.

### 6.3 프론트·백엔드 공동 검증 체크리스트

| 영역 | 확인할 시나리오 |
| --- | --- |
| 로그인 | 정상 계정, 잘못된 비밀번호, 존재하지 않는 이메일, 서버 실패, 연속 탭 |
| 사용자 식별 | 가입 직후뿐 아니라 다른 기기/재설치 후 기존 계정으로 본인 프로필 조회 |
| 이메일 발송 | 정상 발송, 가입/미가입 이메일, 실패, 재전송 제한 |
| OTP | 올바른 코드, 불일치, 만료, 요청 없음, 재전송 전후 코드, 뒤로가기 후 재시도 |
| 회원가입 | 인증하지 않은 가입 요청을 서버가 거부하는지, 인증 후 오래 걸린 가입, 중복 이메일·닉네임, 응답 누락 후 재시도 |
| 조건 저장 | 알레르기 26개 허용 값, 식이조건 복수 선택, 채식 유형, 미선택, 전체 해제, 조회 후 동일하게 복원 |
| 비밀번호 찾기 | 코드가 중간에 소비되지 않는지, 비밀번호 입력 중 만료, 정책 오류, 변경 성공 후 로그인과 기존 세션 처리 |
| 사진 | 미선택 가입, 업로드 성공·실패, 다른 기기 조회, 교체·삭제. 이번 범위에 포함한 경우 |
| Google | 신규/기존 사용자, 같은 이메일 계정, 로그인 취소, 잘못된 Google 토큰, 추가 정보 완료/미선택. 이번 범위에 포함한 경우 |
| 세션·권한 | 앱 재실행, JWT 만료·무효, 권한 부족, 로그아웃, A계정에서 B계정으로 전환 |
| 실제 정보 반영 | 마이페이지와 본인 식이조건에 임시 값이 아닌 서버 정보가 표시되는지 |

일반 사용자 권한으로 본인 조회 성공과 타인 조회 거부를 함께 확인한다. 관리자 테스트 결과만으로 권한 검증 완료로 판단하지 않는다.
