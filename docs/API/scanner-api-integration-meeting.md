# 스캐너 API 연동 협의 회의자료

> 작성일: 2026-10-08\
> 기준: `feature/scanner-api-integration` / `b9dc101`의 코드와 [OCR API 명세](scanner-ocr-api.md)\
> 목적: 상품 검색·상세·판정 계약, 화면 동작, 이번 개발 범위를 함께 확정한다.\
> 상태: **회의 전 초안. 아래 권장안은 미합의이며 실제 서버 호출로 검증하지 않았다.**

> **기초 작업 진행 업데이트 — 2026-10-08:** 사용자 요청에 따라 F1~F10 기반을 구현했다. 실제 카메라·촬영·갤러리·사진 전처리, 분석 상태, OCR 전용 통신과 가짜 응답 테스트, 원격 이미지 표시를 준비했다. **플래시는 촬영 순간에만 발광하는 ON/OFF 방식으로 확정했다.** 실제 OCR 서비스는 DI에서 비활성 구현을 사용하며 분석 버튼도 비활성이다. 상품 검색·판정 API와 제품 정책은 아직 미연결/미합의다. 아래 ‘현재 코드’ 설명은 별도 표기가 없으면 최초 검토 시점 기준이다.

## 0. 회의에서 할 일

현재 API는 **사진에서 상품 검색어를 추출**한다. 사진 속 상품을 DB 상품으로 확정하거나 사용자에게 안전한지 판단하는 기능은 별도로 연결해야 한다.

제안 흐름: **촬영/사진 선택 → 사용자가 분석 실행 → OCR → 상품 검색 → 후보 확인 → 상품 상세·개인화 판정 → 일반 결과/비교 목록**.

오늘은 아래 순서대로 읽고, 각 안건을 **확정 / 추가 확인 / 이번 범위에서 보류** 중 하나로 기록한다. 오늘 모든 답을 얻지 못해도 미정 항목마다 담당자와 회신 기한을 남긴다.

1. [이미 정해진 OCR 규칙](#fixed)을 확인한다.
2. [API 준비 상태](#coverage)를 확인하고 백엔드가 이미 제공하는 기능을 구분한다.
3. [논의 안건 S01~S14](#agenda)를 순서대로 결정한다.
4. [백엔드 자료 요청 목록](#backend-requests)에 담당자·기한을 정한다.
5. [선행 가능한 기초 작업](#foundation)의 착수 범위를 정한다.
6. [결정 기록표](#decisions)를 채운다.

**읽는 기준**

- ‘명세 있음’은 문서 계약을 확보했다는 뜻이다. 서버 호출 성공을 확인했다는 뜻은 아니다.
- ‘앱에 선언 있음’은 Android 호출 코드가 있다는 뜻이다. 백엔드의 실제 구현·배포를 보장하지 않는다.
- ‘명세 미확보’는 서버 기능이 없다는 뜻이 아니다. 기존 기능의 문서를 받는 것이 먼저다.
- 새 API가 필요한지, 기존 API 확장이나 프론트 처리로 충분한지는 안건별로 판단한다.
- 모든 합의가 끝날 때까지 카메라·파일 처리까지 기다릴 필요는 없다.

## 1. 이미 정해진 OCR 규칙

원본 계약은 [OCR 명세](scanner-ocr-api.md)를 따른다. 변경을 원한다면 별도 서버 변경 합의가 필요하다.

| 항목 | 확정된 계약 | 프론트 반영 사항 |
| --- | --- | --- |
| 역할 | `POST /api/ocr`는 검색어 추출 | OCR 성공과 상품 확정·SAFE를 구분 |
| 인증 | `X-OCR-Test-Token`, 회원 JWT 불필요 | 팀 내부 테스트용으로만 사용. 401을 회원 로그아웃으로 연결하지 않음 |
| 요청 | multipart `image` 파일 1개, 추가 필드·쿼리 없음 | 알레르기·프로필·검색어를 OCR 요청에 추가하지 않음 |
| 사진 | JPEG/PNG, 최대 10MiB·2,000만 픽셀, 전체 요청 최대 10MiB+64KiB | 형식·크기·픽셀·회전 검사. HEIC/WebP는 실제 변환 필요 |
| 실행 | 사진 선택과 분석 실행 분리 | 선택 직후 자동 호출하지 않음 |
| 성공 응답 | HTTP 200이어도 `OK` / `NO_TEXT` / `NO_SEARCH_KEYWORD`로 구분 | `OK`인데 검색어가 없으면 비정상 응답 처리 |
| 필드 의미 | `warnings`는 현재 빈 배열, `evidence`는 추출 근거 | 알레르기 경고·상품 일치 신뢰도로 사용하지 않음 |
| 용량 | `totalWeight`는 `500ml` 같은 문자열 | 영양성분의 100g/1회 제공량 기준으로 사용하지 않음 |
| 대기 | 클라이언트 150초 이상 권장, 서버 전체 응답 대기 최대 135초 | 긴 대기 상태 처리. 150초가 예상 소요시간은 아님 |
| 재요청 | 자동 재전송 금지, 요청 ID 기반 중복 제거 없음 | 연속 터치·회전·재진입·통신 계층 재전송 방지 |
| 제한 | 서버 전체 동시 1건·최소 간격 3초 | 비교 사진을 병렬 OCR 처리하지 않음. 429 자동 반복 금지 |
| 비용 | 팀 전체 유료 LLM 누적 1,000회 | 일일·개인별 한도가 아님. 실패·결과 불명 시도도 자동 환급하지 않음 |
| 요청 ID | 헤더 중계 ID와 본문 OCR 작업 ID는 별개 | 각각 진단용으로 보관. 상태 조회·취소 기능으로 간주하지 않음 |
| 접속·외부 전송 | 요청 기기의 Tailscale 접근 필요. 사진은 AWS OCR, 추출 문구·좌표는 OpenAI로 전송 | 테스트 기기 접근 확인과 사진 업로드 안내에 반영 |

## 2. 현재 기반과 확보해야 할 API

| 기능 | 확인된 상태 | 필요한 조치 |
| --- | --- | --- |
| OCR | 명세 확보, 전용 통신·모델·상태 기반 구현 | 접속·토큰 운영 합의 후 실제 호출 검증 및 서비스 활성화 |
| 상품 검색 | `GET /api/products/search` 선언 있음 | 요청값·후보 식별 정보·검색 결과 없음 계약 확보 |
| 상품 상세 | `GET /api/products/{barcode}` 선언 있음 | 바코드/ID, 이미지·영양·원재료·알레르기 계약 확보 |
| 개인화 판정 | 상품 응답 DTO에 `analysis`와 `verificationRequired` 있음 | 입력 대상·판정 기준·정보 부족 의미 확인. 별도 endpoint가 필수인 것은 아님 |
| 안전 추천 | `GET /api/products/safe-recommendations` 선언 있음 | 특정 상품의 대체품까지 지원하는지 확인 |
| 챗봇 | `POST /chat`, 상품 전달 모델 있음 | 동일 상품·대상 프로필 전달과 추천 응답 계약 확인 |
| 비교 | 목록·레포트 UI가 있으나 고정 샘플 사용 | 개별 결과 집계인지 서버 비교/순위 기능인지 결정 |
| 이력·OCR 상태 조회·취소 | 이번 명세에 없음 | 이번 범위에 필요한지부터 결정 |

화면·버튼·팝업·Retrofit/Hilt 기반은 재사용 가능하다. 최초 검토 때는 고정 카메라 배경과 셔터 샘플 결과였으나, F1~F5 작업으로 실제 카메라·사진 상태 ViewModel을 추가했다. OCR 서비스·분석 상태 기반도 추가했으며 상품 검색·결과 연결은 아직 필요하다.

## 3. 프론트·백엔드·제품 공동 논의 안건

### S01. 이번 버전의 범위

**결정할 것**

- 일반 스캔, 비교, 상세 이동, 챗봇, 대체 추천 중 이번 완료 범위는 어디까지인가?
- 인식 대상은 상품 한 개의 포장 전면 사진인가? 일반 음식 사진·바코드 인식도 필요한가?
- 팀 내부 시연용인가, 일반 사용자에게 배포할 버전인가?

**권장안:** 포장 상품 한 개의 OCR → 상품 검색 → 일반 결과를 먼저 완성하고 비교와 후속 동작을 연결한다. 일반 음식 영양 분석·바코드 디코딩은 현재 OCR 계약으로 지원한다고 가정하지 않는다.

**남길 결정:** 포함/보류 기능, 대상 사진, 배포 범위, 완료 기준.

### S02. 상품 검색과 후보 확정 — 기존 B1·U1

**현재:** OCR은 DB 상품 ID를 주지 않는다. 앱의 상품 검색은 결과를 이름 유사도 등으로 재정렬하며, 첫 결과가 정답이라는 보장은 없다.

**백엔드 질문**

- `searchKeyword`를 그대로 검색에 전달할 수 있는가? 검색어 길이·인코딩·페이지/개수·정렬 규칙은?
- 후보에 바코드/상품 ID, 이름, 브랜드, 이미지, 맛·용량이 있는가? 바코드가 없는 상품도 있는가?
- 후보 없음과 서버 오류의 응답은? 같은 이름의 다른 맛·용량을 어떻게 구별하는가?
- 별도 일치 점수나 확정 기준이 있는가? 없다면 프론트가 임의로 추정하지 않는다.

**화면 선택지:** 항상 확인 / 후보 1개이면 자동 확정 / 서버가 보장하는 일치 기준을 만족할 때만 자동 확정.

**권장안:** 초기에는 1개여도 사용자 확인을 거친다. OCR에 브랜드·용량이 있다고 검색어에 임의로 덧붙이지 않는다. 검색 계약에 맞춰 활용한다. 사용자 수정 검색은 OCR 추출값과 구분한다.

**남길 결정:** 검색 요청·응답, 확정 식별자, 후보 확인 방식, 후보 화면 담당자.

### S03. 상품 상세·이미지·영양 데이터 — 기존 B2

**백엔드 질문**

- 검색 결과의 어떤 값으로 상세를 조회하는가? 바코드가 없거나 상품이 삭제됐을 때는?
- 이미지 URL의 접근 인증·만료 여부와 이미지 없는 경우의 값은?
- 원재료·알레르기는 원문 문자열인가, 공통 ID 목록인가? 교차오염/혼입 가능성 안내는 별도인가?
- 영양 수치는 100g당, 100ml당, 1회 제공량당, 총 내용량당 중 무엇인가? 단위와 기준량을 응답으로 구분할 수 있는가?
- 미측정/정보 없음과 실제 0은 어떻게 구분하는가? 칼슘·카페인·식이섬유도 제공하는가?

**현재 차이:** 결과 팝업은 100g 안내가 고정돼 있고, 기존 상품 DTO는 7개 영양성분만 가진다. UI 샘플의 모든 성분을 받을 수 있다고 가정할 수 없다.

**남길 결정:** 상세 식별자, 필드·단위·nullable 규칙, 이미지 접근 방법, 제공 가능한 성분 목록.

### S04. 안전·주의·정보 부족 판정 — 기존 B3·U3

**백엔드 질문**

- 알레르기만 판단하는가, 저당·고단백·글루텐프리·채식 유형 등도 판단하는가?
- 누가 판정 기준을 관리하는가? 식이조건의 수치 기준·적용 기준량은 무엇인가?
- `status`, `isDangerous`, `verificationRequired` 각각의 의미와 서로 충돌할 때 우선순위는?
- 성분 미등록, 원재료 불완전, 교차오염 가능성은 어떻게 판단하는가?
- 주의 대상 성분·조건·이유를 구조화된 값으로 받을 수 있는가?

**화면 결정:** 정보 부족 표시, SAFE/Warning/DANGER 문구 통일 여부, 경고 영역에 표시할 이유, 알레르기 주의와 식이조건 불일치의 구분.

**권장안:** ‘확인 필요’를 별도 상태로 표시하고 정보 부족을 SAFE로 바꾸지 않는다. 판정은 합의된 서버 계약을 따르며 임의 문자열 포함 검사로 새 기준을 만들지 않는다.

**현재 보완:** 스캐너에는 Safe/Warning만 있다. 상품 DTO의 `verificationRequired`는 도메인 모델까지 전달되지 않는다.

**남길 결정:** 상태 대응표, 판정 책임, 근거 필드, 각 상태의 문구·디자인.

### S05. 분석 대상과 알레르기·식이조건 코드 — 기존 U4

**함께 결정할 것**

- 본인만 분석하는가, 홈/상품 화면의 선택 가족을 이어받는가? 선택 대상이 없으면?
- 서버 사용자 ID, 가족 ID, 조건 목록 중 무엇을 전달하는가? 비로그인 상태도 가능한가?
- 알레르기와 식이조건은 공통 카탈로그의 ID로 보내는가? 배열/쿼리 표현과 빈 목록 의미는?
- 여러 명일 때 한 명이라도 주의이면 전체 주의인가? 누구의 어떤 조건인지 각각 반환 가능한가?
- 주의 대상과 정보 부족 대상이 섞이면 어떻게 집계하는가?
- 분석 중이나 비교 도중 대상을 바꾸면 기존 결과를 다시 판정하는가, 세션 동안 고정하는가?

**현재 차이:** 로컬 프로필의 `me`/UUID는 서버 Long 사용자 ID와 다르다. 기본 가족 데이터도 실제 서버 계정이라고 가정하면 안 된다. 프로필 선택 상태는 화면별로 분리돼 있고 스캐너로 전달되지 않는다. 코드 경로별로 조건명·코드 변환도 다르다.

**권장안:** 분석 대상을 화면에 명시하고, 결과에 분석 당시 대상을 연결한다. 여러 대상의 판정 의미를 합의하기 전에는 임의로 조건을 합쳐 ‘모두에게 안전’이라고 표시하지 않는다.

**남길 결정:** 입력 계약, 코드 목록, 다중 대상 집계 규칙, 대상 변경 정책.

### S06. 촬영·사진 선택·분석 시작 화면

**확정된 제약:** 사진 선택만으로 OCR을 호출하지 않는다. 상품 한 개의 전면 사진이 권장 입력이다.

**결정할 것**

- 촬영/갤러리 선택 후 사진 확인 화면에서 ‘분석하기’를 누르는 흐름으로 할 것인가?
- 사진 교체·재촬영 동작과 업로드 안내는 어디에 둘 것인가?
- 카메라 가이드 사각형은 위치 안내인가, 실제로 잘라서 보낼 영역인가?
- **확정(2026-10-08 사용자 요청): 촬영 순간 플래시 ON/OFF.** 계속 켜지는 조명은 사용하지 않는다. 미지원 카메라에서는 버튼을 비활성화한다.

**권장안:** 사진 확인 후 명시적으로 실행한다. 우선 가이드라인은 안내로 사용하고 자동 자르기는 별도 합의한다. 촬영과 사진 선택의 공통 결과를 하나의 이미지 상태로 관리한다.

**선행 가능:** 최종 확인 화면 디자인이 없어도 권한·미리보기·촬영 파일 생성·갤러리 선택은 구현할 수 있다.

**남길 결정:** 촬영 후 흐름, 분석 버튼 위치, 가이드/플래시 의미, 디자인 담당자.

### S07. 실패·긴 대기·재시도·화면 이탈 — 기존 U2

| 상황 | 결정할 화면 동작 / 권장 방향 |
| --- | --- |
| 글자 없음·검색어 없음 | 원인에 맞는 안내 + 재촬영/사진 선택 + 직접 검색 경로 |
| 상품 검색 결과 없음 | 사용자가 검색어를 수정하거나 다시 촬영. OCR 재호출과 DB 재검색을 구분 |
| 분석 대기 | 로딩과 중복 실행 차단. 서버 진행률이 없으므로 가짜 퍼센트/완료 시각 표시 금지 |
| 429 사용 중/간격 제한 | 안내 후 사용자 동작으로 재시도. Retry-After를 자동 반복 예약으로 사용하지 않음 |
| 타임아웃·연결 종료 | 서버 처리 여부가 불명확할 수 있음을 고려한 안내. 자동 재전송 금지 |
| 화면 뒤로가기·앱 종료 | 나가기 허용/확인 여부, 사진·상태 보존 범위 결정. 앱 요청 취소가 서버 취소를 보장하지 않음 |
| 복귀·회전 | 새 요청 자동 실행 금지. 진행 중 상태·결과를 어떻게 보여줄지 결정 |
| 401·503·비JSON 오류 | 내부 테스트 인증/서비스 문제를 일반 로그인 실패와 구분. 서버 원문을 그대로 노출하지 않음 |

**백엔드 질문:** 공개 운영에서도 긴 동기 대기를 유지할 것인가? 결과 조회·취소·중복 방지가 필요한가? 추가할 경우 별도 계약을 정한다. 현재 요청 ID만으로 가능한 기능은 아니다.

**남길 결정:** 실패별 버튼·안내, 명시적 재시도 정책, 이탈·복귀·사진 보존 정책, 확장 여부.

### S08. 결과 팝업의 영양 4칸과 경고 영역

**결정할 것**

- 항상 공통 성분 4개인가, 제공 데이터/상태에 따라 달라지는가? 우선순위는?
- 4개보다 적으면 칸을 줄이는가, ‘정보 없음’으로 표시하는가?
- 기준량을 확인할 수 없으면 어떻게 안내하는가?
- 주의 이유가 여러 개면 모두 표시/요약 후 펼치기 중 무엇을 사용할까?
- 상품명이 길거나 이미지가 없을 때 표시 방식은?

**권장안:** S03의 제공 성분·단위를 먼저 확인하고 구성한다. 누락값을 0으로 채우지 않는다. 표시를 요약해도 원본 알레르기·판정 근거는 보존한다. 기존 UI 간격·원형 이미지 가림 수정은 유지한다.

**남길 결정:** 성분 우선순위, 누락 표시, 기준량 문구, 경고 표시 방식.

### S09. 비교 목록·분석 레포트

**현재:** 목록은 개수만 저장하며 초기 1개/최대 8개다. 레포트는 별도 고정 상품 3개를 보여준다. 이 값들은 서버 계약이 아니다.

**결정할 것**

- 최소 2개·최대 8개를 유지할까? 동일 상품은 중복 추가를 막을까? 다른 맛·용량은 어떻게 구분할까?
- 정보 부족 상품을 비교에 포함할까? 인식만 되고 상품 확정이 안 된 사진은?
- ‘추천’은 안전한 상품 개수인가, 조건에 가장 적합한 순위인가? 동점·모두 주의·모두 정보 부족이면?
- 영양 비교를 한다면 기준량을 통일할 수 있는가? 질량/부피 변환을 임의로 하지 않는다.
- 삭제·마지막 상품 제거·비교 화면 복귀·대상 변경 시 목록과 집계는 어떻게 유지할까?

**권장안:** 확정 상품 ID로 목록을 관리하고 같은 목록에서 레포트를 만든다. 단순 개별 결과 집계면 프론트에서 가능하다. 별도 추천 순위·종합 판정이 필요하면 기준과 서버 지원을 추가로 정한다. 레포트를 열 때 OCR을 다시 실행하지 않는다.

**남길 결정:** 개수·중복·정보 부족 규칙, 추천 의미, 집계 책임, 세션 보존 범위.

### S10. 상품 상세·챗봇·대체 추천 연결

**함께 확인할 것**

- 상세 화면에는 확정한 상품 ID와 같은 분석 대상을 전달할 수 있는가?
- 챗봇은 어떤 상품·프로필 필드를 요구하는가? 질문 문구만으로 전달할지 구조화된 상품 맥락도 전달할지?
- 현재 챗봇은 요청의 profiles와 chat_history를 채우지 않는다. 필요한 범위와 대화 이어가기 계약은?
- 안전 추천은 동일 카테고리의 대체품을 지원하는가? 원래 상품 제외, 알레르기/식이조건 반영, 결과 없음 처리 방법은?
- 기존 챗봇 응답 처리에서 사용하는 `product_candidate` 외 추천 유형도 이번 흐름에서 필요한가?
- 이번에 연결하지 않는 버튼은 숨김/미지원 안내 중 어떻게 처리할까?

**권장안:** 확정 상품과 분석 대상이 유지되도록 연결한다. 일반 안전 추천을 특정 상품의 대체 추천으로 이름만 바꿔 사용하지 않는다.

**남길 결정:** 화면 이동 입력, 챗봇·추천 계약, 후속 보류 버튼 처리.

### S11. 서버 환경·인증·팀 테스트 운영

**백엔드 요청**

- 상품·챗봇 서버 주소, 인증 방법, 명세 버전과 현재 배포 버전.
- OCR Tailscale 접속을 에뮬레이터/실기기 각각 어떻게 검증할지. PC 접속 성공만으로 기기 접속을 확인한 것으로 보지 않는다.
- 팀 토큰 전달·교체 담당자와 테스트 가능 시간. 토큰 원문은 문서·Git·로그에 적지 않는다.
- 공용 동시 1건/누적 예산의 테스트 일정·실패 보고 담당자. 남은 예산은 응답에 없으므로 확인 경로는?
- 503에서 예산 소진과 서비스 준비 문제를 구분할 운영 확인 방법은?
- 일반 사용자 배포를 포함한다면 공개용 접근·인증·이용 제한 계약은?

**현재 차이:** 앱은 상품/AI용 로컬 주소와 공용 30초·BODY 로그 설정을 사용한다. OCR은 별도 클라이언트로 분리할 계획이다. 로그인 API 미완료가 OCR 자체를 막지는 않지만 상품·판정의 인증 의존성은 확인해야 한다.

**남길 결정:** 환경별 주소·인증, 기기 접속 담당, 테스트 시간·예산 확인 방법, 운영 전환 범위.

### S12. 사진·결과 보존과 스캔 이력

**결정할 것**

- 사진은 현재 작업 동안만 보관하는가? 수동 재시도와 앱 재시작까지 보관하는가? 언제 삭제하는가?
- 스캔 이력을 이번에 제공하는가? 제공한다면 상품 ID·판정 당시 대상·시간·사진 중 무엇을 저장하는가?
- 저장 장소는 기기/서버 중 어디인가? 다시 열 때 당시 판정을 보여줄까, 최신 조건으로 다시 판정할까?
- 명세에 적힌 외부 전송을 어디에서 안내할까? 서버 측 보관·삭제 설명이 필요하면 담당자는?

**권장안:** 업로드가 끝나기 전에 임시 파일을 지우지 않는다. 이력 기능과 서버 보관 정책은 별개로 확인한다. 원본 사진이나 인식 문구를 디버그 로그로 남기지 않는다.

**남길 결정:** 사진 수명, 이력 포함/보류, 저장·재조회 계약, 안내 문구 담당자.

### S13. 실제 데이터 연동 전에 정리할 프론트 코드

아래는 제품 정책을 새로 정하는 일보다 기존 코드의 데이터 손실·오동작을 방지하는 작업이다. 다른 화면도 사용하는 공통 코드라 영향 범위를 함께 확인한다.

| 현재 문제 | 수정 방향 |
| --- | --- |
| 상품 검색/상세 실패를 샘플 데이터로 대체 | 실제 연동 경로에서 실패를 숨기지 않도록 개발용 샘플 분리 |
| `verificationRequired` 전달 누락 | S04 계약에 맞춰 도메인·화면까지 보존 |
| 알레르기 목록을 데이터 변환에서 최대 3개로 제한 | 전체 정보 보존, 개수 제한은 표시 계층에서 처리 |
| 공통 이미지 선택기에서 촬영 콜백 직후 파일 삭제 | 비동기 처리에 맞게 파일 소유권·정리 시점 변경. 기존 프로필 사진 흐름 회귀 확인 |
| 스캐너 모델이 로컬 drawable만 지원 | 원격 이미지·상품 식별자·정보 부족·판정 근거를 전달하도록 확장 |
| URL 이미지용 네트워크 모듈 선언 없음 | 현재 Coil 버전에 맞는 네트워크 모듈 및 실패 이미지 처리 |
| 취소 예외가 일반 실패/샘플 대체에 섞일 수 있음 | 작업 취소 보존, 오래된 응답으로 새 사진/대상의 상태 덮어쓰기 방지 |

**남길 결정:** 공통 코드 담당자, 수정 순서, 기존 상품·프로필·스캐너 UI 회귀 범위.

### S14. 검증 데이터와 완료 기준

**백엔드에 필요한 예시:** 정상 후보 1개/여러 개/0개, 바코드 없음, 정상 상세, 주의 판정, 정보 부족 판정, 영양 누락, 다중 가족 판정, 추천 없음, 각 API 오류 응답.

**프론트 검증:** OCR 200의 3개 상태, 빈 검색어/비JSON, 401/429/503/504, 파일 제한·손상·회전, 연속 터치·회전·재진입의 중복 요청, 대상 변경, 목록 추가·삭제·0개, 이미지 없음, 누락값과 0 구분.

**권장안:** 가짜 응답 테스트로 상태 처리를 먼저 검증하고, 실제 서버는 팀과 정한 데이터·시간에 소량 호출한다. 카메라·플래시는 에뮬레이터와 실기기 검증 범위를 나눠 기록한다.

**남길 결정:** 테스트 데이터 담당자·기한, 검증 기기, 기능별 합격 기준, 실제 호출 일정.

## 4. 백엔드에 전달할 자료 요청 목록

아래는 복사해서 요청할 수 있는 목록이다. 새 API 개발 요청으로 일괄 해석하지 말고, 기존 구현/명세의 제공 여부부터 확인한다.

- [ ] **B1 상품 검색:** 요청·응답·빈 결과·오류 예시, 후보 식별자·이미지·맛/용량, 검색 제한·정렬. 관련 S02.
- [ ] **B2 상품 상세:** 식별자, 영양성분·단위·기준량·null 규칙, 이미지·원재료·알레르기 형식. 관련 S03·S08.
- [ ] **B3 개인화 판정:** 대상 전달법, 알레르기·식이조건 코드, 상태·근거·정보 부족, 다중 가족 처리. 관련 S04·S05.
- [ ] **B4 챗봇·대체 추천:** 상품 맥락·대상 전달, 대체품 범위·제외 조건·응답 유형. 관련 S10.
- [ ] **B5 접속·운영:** 환경별 주소·인증 방법·배포 버전, 기기 접속, 팀 테스트 운영 담당. 실제 비밀값은 별도 비공개 경로 사용. 관련 S11.
- [ ] **B6 검증 데이터:** 위 계약을 확인할 테스트 상품·프로필과 상태별 응답 예시. 관련 S14.
- [ ] **선택 확장:** S07·S09·S12에서 이번 범위로 정한 경우에만 OCR 결과 조회/취소/중복 방지, 서버 비교·순위, 이력 저장 계약 추가.

## 5. 회의 결과를 기다리지 않고 진행 가능한 기초 작업

**카메라와 사진 준비는 상품 API 계약과 독립적으로 구현할 수 있다.** 아래 F1~F10의 기초 구현을 완료했다. 실제 OCR 호출·상품 확정·개인화 판정까지 완료했다는 뜻은 아니다.

| 순서 | 작업 | 규모 | 완료했을 때 확인할 것 | 선행 합의/주의점 |

### 구현한 기반과 검증 범위

- **F1~F5:** 권한·실제 미리보기·촬영·Photo Picker·파일 수명을 연결했다. 화면 회전 중 사진을 유지하며 교체/재촬영/종료 시 앱 자체 파일만 정리한다. 갤러리 원본은 변경하지 않는다. 이전 프로세스 잔여 파일은 다음 스캐너 진입에 정리한다. 프로세스 재시작 복원은 미구현이다.
- **F6:** 로컬 원본 입력은 최대 50MiB로 제한하고, 큰 사진은 전체 크기로 메모리에 올리기 전에 축소 디코딩한다. 긴 변 최대 2048px, 흰 배경 JPEG로 변환하고 EXIF 8방향 회전·반전을 적용한다. 출력의 10MiB·2,000만 픽셀·실제 JPEG 형식을 다시 확인한다. 50MiB는 로컬 가져오기 한도이며 서버 업로드 한도를 변경한 것이 아니다. PNG/WebP 및 기기에서 디코딩 가능한 정적 HEIF/HEIC를 변환하며 애니메이션 PNG/WebP·HEIF 시퀀스는 거부한다. 출력에 원본 GPS/EXIF를 복사하지 않는다. 자동 크롭은 하지 않는다.
- **F7:** 분석 대기/진행/결과·오류 상태를 분리했다. 중복 실행을 막고 사진 교체·종료 후 늦은 응답은 무시한다. 사진 선택/회전만으로 요청하지 않는다. 최종 후보 선택·판정 UX는 합의 후 구현한다.
- **F8:** OCR 전용 서비스는 multipart `image` 하나만 전송하도록 구현했다. JWT·BODY 로그 없이 토큰 공급 경로를 분리하고 read 150초/call 240초를 설정했다. 자동 재시도·리다이렉트·인증 재전송을 끄고 one-shot 본문으로 408/503 재전송도 막는다. 상태 3종·nullable 필드·비정상 응답·429/Retry-After·요청 ID 2종을 구분한다. **운영 DI는 `UnavailableScannerOcrService`이며 실제 주소/토큰 주입과 서버 호출은 하지 않았다.**
- **F9:** Coil 네트워크 모듈과 별도 이미지 클라이언트를 연결했다. 결과/레포트 이미지 컴포넌트에 URL·로딩·없음/실패 표시를 추가했다. 이미지 요청에 OCR/회원 인증 헤더를 넣지 않는다. 원형 이미지 뒤 흰 배경도 유지한다.
- **F10:** CameraX 촬영 플래시 ON/OFF를 셔터 실행에 적용한다. 지원 여부·준비 상태에 따라 버튼을 활성화하며 켜짐 상태를 표시한다. 지속 조명은 사용하지 않는다. 실제 발광은 플래시가 있는 실기기에서 확인해야 한다.
- 실제 사진에 샘플 SAFE/Warning을 붙이지 않는다. 비교 목록은 확정 상품이 없으므로 0개이며 기존 결과·레포트 UI는 보존했다. 사진 확인 화면은 기초 검증용이며 최종 디자인 합의를 대신하지 않는다.
- 최종 APK 수동 확인: 실제 미리보기 → 셔터 → JPEG 사진 확인 정상, 처리 후 세션에 결과 파일 1개만 유지. 에뮬레이터의 플래시 미지원 상태에서 버튼 비활성, 분석 버튼 비활성 안내 확인.
- **검증:** `:app:assembleDebug :app:testDebugUnitTest :app:connectedDebugAndroidTest -Pandroid.testInstrumentationRunnerArguments.package=com.coworker.jjikmuk.feature.scanner` 성공. 단위 테스트 40개와 스캐너 기기 테스트 7개 모두 통과했다. 단위 테스트는 파일 수명·상태·파싱·단일 multipart·408/429/503/redirect/timeout 재전송 방지·취소를 확인한다. 기기 테스트는 EXIF 8방향 픽셀 변환·큰 PNG·투명 배경·WebP·APNG 거부·손상 사진·Coil 로딩/404와 인증 헤더 미전송을 검증한다. 실제 OCR 서버·실기기 플래시·HEIF 기기별 디코딩은 별도 확인 대상이다.

**아직 계약/화면 결정이 필요한 작업:** 상품 자동 확정, SAFE/주의 기준, 가족 집계, 영양 표시 선택, 비교 추천 순위, 챗봇/대체 추천 연결, 이력 저장. 해당 합의 전에는 동작을 임의로 고정하지 않는다.

CameraX는 미리보기와 사진 촬영을 분리된 기능으로 제공하므로 위처럼 나눠 개발할 수 있다. [Android 미리보기 문서](https://developer.android.com/media/camera/camerax/preview), [사진 촬영 문서](https://developer.android.com/media/camera/camerax/take-photo). Coil 3 URL 이미지의 네트워크 모듈 요구사항은 [공식 문서](https://coil-kt.github.io/coil/network/)를 참고한다.
