## 현재 결론

Refresh/Google 경로의 과거 명세 차이도 이번 발송 확인만으로 해결됐다고 보지 않는다.

## 2026-11-01 로그인 후 본인 정보 조회 차단 — hasPassword 누락

사용자는 계정 생성 성공 후 로그인에서 ‘요청을 처리하지 못했어요 / 다시 확인 / 로그아웃’ 화면을 보고했다. 저장된 세션으로 `GET https://43.203.42.36/api/users/me`를 1회 조회했다. 비밀번호 재입력·계정 재생성·토큰 갱신·서버 데이터 변경 없이 확인했다.

- 응답 Date: **2026-11-01 03:34:14 KST** (2026-10-31 18:34:14 GMT).
- 저장된 Access는 조회 시점에 **미만료**, HTTP **200**, 응답 `data.id`는 저장된 세션 사용자와 일치.
- 응답 최상위: `message:string`, `data:object`.
- `data` 필드: `id:number`, `email:string`, `nickname:string`, `allergies:string`, `diseases:null`, `specialDiet:string`, `dislikedIngredients:null`, `role:string`, `authProvider:string`, `profileCompleted:boolean`.
- **`data.hasPassword`가 없음.** 인증 v2 명세의 본인 조회 예시는 boolean으로 제공한다. 앱 `AuthResponseMapper.profile()`은 필수 값으로 검사하기 때문에 `InvalidResponse`가 되어 홈 진입이 중단된다.
- 계정/비밀번호 불일치나 이번 GET의 500 문제가 아니다. 필드 누락이라는 명세·배포 응답 불일치가 확인됐다. 다른 잠재적 필드 문제까지 모두 배제한 검증은 아니며, 수정 후 실제 앱에서 다시 확인해야 한다.

백엔드에는 본인 조회 응답에 실제 비밀번호 보유 여부인 `hasPassword` boolean을 포함하도록 요청한다. 일반/연결 계정은 true, Google 전용 계정은 false라는 기존 계약을 확인한다. 같은 프로필 DTO를 쓰는 PATCH/프로필 완료 응답도 함께 점검하고 실행 중인 배포 버전을 확인한다. `photoUrl`도 없었지만 앱은 선택 필드로 허용하므로 이번 차단 원인은 아니다.

명시적 실행 옵션 `inspectStoredProfile=true`가 있어야 수행되는 `StoredProfileDiagnosticTest`로 확인했다. 테스트는 세션을 읽고 GET 한 번만 수행하며 저장 상태를 바꾸지 않는다. 출력에는 토큰·이메일·닉네임·조건 값·사용자 ID를 포함하지 않았다. 일반 테스트 실행에서는 건너뛴다.

## 2026-11-01 이메일 발송 후 화면 전환 실패 확인

사용자가 허용한 테스트 이메일로 `POST /api/auth/email/send`를 **1회만** 호출했다. `purpose=signup`, Authorization 없이 정상 HTTPS 검증을 사용했고 자동 재시도하지 않았다.

| 항목 | 실제 관측 |
| --- | --- |
| HTTP 결과 | 200 |
| 연결 시간 / 첫 응답 / 전체 시간 | 0.032초 / 32.382초 / 32.382초 |
| 서버 Date | 2026-10-31 17:46:10 GMT = 2026-11-01 02:46:10 KST |
| `data.email`, `data.purpose` | 요청한 이메일·`signup`과 일치 |
| `data.expiresInSeconds` | 300 |
| `data.expiresAt` | `2026-10-31T17:50:38.2502111` — 시간대 없음 |
| `data.resendAvailableAt` | `2026-10-31T17:46:38.2502111` — 시간대 없음 |

기존 인증 클라이언트는 읽기 제한 30초였으므로 이 응답을 기다리지 못한다. 네트워크가 더 빨라도 기존 파서는 시간대 없는 날짜를 거부한다. 두 경우 모두 ‘처리 결과를 확인하지 못했어요’와 60초 재요청 제한으로 처리되어 OTP 입력 화면으로 이동하지 않는다. 메일 도착 자체를 앱의 발송 성공으로 간주할 수는 없다.

프론트 대응:

- **메일 발송에만** 읽기 제한 60초·전체 요청 제한 75초 적용. 다른 인증 요청의 30초/45초 제한은 유지한다.
- 이메일 발송·OTP 검증 응답에서 시간대가 없는 유효한 날짜는 절대시각으로 변환하지 않는다. 검증된 `expiresInSeconds`와 요청 시작 시점 기준 타이머를 사용한다. 대기한 32초를 되돌려 5분을 새로 시작하지 않는다.
- 시간대가 있는 응답은 기존대로 해석한다. 잘못된 날짜·다른 이메일/용도·잘못된 유효시간은 계속 거부한다. 로그인·Refresh·Google 증명의 시간대 검증은 엄격하게 유지한다.
- 자동 재발송·리다이렉트·TLS 검증 우회 없음. 결과를 끝내 확인하지 못한 요청은 성공으로 바꾸지 않는다.

백엔드 확인 사항은 [통합 협의안 R1](../협의/로그인-회원가입-백엔드-협의안.md)에서 관리한다. 발송 지연 개선과 `expiresAt`/`resendAvailableAt`의 시간대 포함 응답이 필요하다. 저장소 소스의 offset 변환 코드와 배포 응답이 달라 실행 버전 확인도 필요하다. OTP 검증 응답의 같은 날짜 호환은 코드/테스트로 대비했으며 실제 서버 OTP 검증은 아직 수행하지 않았다.

수정 후 검증: 단위 테스트 **259개 통과**, `assembleDebug` 성공. MockWebServer에서 **31초 응답 지연 + 실제 배포 형태의 offset 없는 날짜**를 함께 재현해, 발송 성공 → OTP 입력 가능 상태 → 검증 성공을 확인했다. 이메일/용도/유효시간 오류와 잘못된 날짜, 세션 offset 누락은 계속 거부하며 발송 자동 재시도도 차단된다. 수정 APK를 실행 중인 AVD에 `install -r`로 업데이트하고 실제 `MainActivity` 실행을 확인했다. 앱 데이터는 삭제하지 않았다. 실제 서버 가입·로그인 완료 검증을 대체하는 테스트는 아니다.

### 로그인 Authorization 자동 첨부 추가 확인

백엔드 질문에 따라 실제 앱의 AuthModule → HttpAuthRepository → AuthApi 경로를 확인했다. 인증 전용 OkHttpClient에는 JWT 자동 첨부 인터셉터가 없고 login은 Body만 받는다. MockWebServer 테스트에서 같은 Repository로 Bearer를 붙인 GET me를 먼저 수행한 뒤 POST /api/auth/login을 호출했다. 후속 로그인 요청에 Authorization이 없으며 JSON 키는 email/password 두 개뿐임을 확인했다. 해당 Repository 테스트 20개 통과.

이는 앱의 HTTP 요청 생성 검증이며 사용자가 앞서 수행한 실서버 로그인 패킷을 소급 캡처한 것은 아니다. 해당 로그인 실패 HTTP/code/message 원문은 확보하지 않았다. 실제 확보한 오류 근거는 로그인 이후 GET me의 HTTP 200 및 hasPassword 누락이다. 화면의 ‘요청을 처리하지 못했어요’는 앱이 InvalidResponse에 표시한 문구이며 서버 오류 message를 그대로 표시한 것이 아니다.
