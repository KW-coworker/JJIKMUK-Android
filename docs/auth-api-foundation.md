# 인증 API 기반 작업

> 기반 작업(PR #22는 후속 브랜치로 대체하여 병합 없이 닫음) 기준: [인증 API 명세](API/auth-api.md), 2026-10-21 사용자 결정, 2026-10-23 로그인·세션 작업 반영. 실제 서버 연결 검증 전 단계.

## 2026-10-29 3단계 업데이트 — 본인 조회·시작 복원·닉네임 PATCH

- `GET /api/users/me`, `PATCH /api/users/me`를 신뢰한 인증 서버에만 명시적 Bearer로 호출한다. 응답은 `data`의 Profile이며 현재 계정의 ID·정규화 이메일과 일치해야 반영한다.
- 저장된 세션이 있으면 스플래시 → 시작 확인 화면으로 이동한다. 없으면 기존 권한 안내 → 인증 선택 흐름을 유지한다. 로그인 성공 직후도 me 확인 후 홈으로 이동한다. Access 만료는 기존 단일 Refresh 처리 후 조회하며, 서버의 만료 응답에 대한 GET 재전송은 최대 1회다.
- 일반 통신 실패·503·403·잘못된 본문은 세션을 보존하고 재확인 UI를 표시한다. 명시적 무효 토큰은 세션 정리 후 인증 선택으로 이동한다. Refresh 응답 유실/소비 여부 불확실 정책은 2-2와 동일하다.
- `AuthProfiles`가 me/PATCH를 직렬화하고 세션 세대와 계정 ID를 확인한다. 계정 전환 뒤 늦은 결과·대기 중이던 수정은 반영하지 않는다. 프로필 응답이 갱신과 겹쳐도 현재 토큰 쌍을 보존하며, 메타데이터만 바뀐 것을 토큰 갱신으로 착각하지 않는다.
- 마이페이지 상단 및 프로필 편집의 예시 닉네임/이메일을 서버 me 값으로 교체했다. 편집 진입 시 최신 조회, 입력 검증, 저장 버튼, 중복/통신 실패 안내를 기존 토큰·버튼으로 구성했다. 닉네임만 PATCH하므로 알레르기·식이조건을 재전송하거나 지우지 않는다.
- 본인 닉네임 유지/대소문자 변경은 공개 중복 확인 결과로 막지 않는다. 최종 중복 오류는 PATCH 응답으로 처리하고 입력을 유지한다. 결과 유실·갱신 후 수정 재확인이 필요하면 저장 반복을 막고 GET me 확인 후 사용자가 다시 저장한다. 자동 PATCH 재전송 없음.
- **범위 경계:** `profileCompleted=false`는 별도 안내/재확인/로그아웃 경로로 분기하고 홈을 막는다. 실제 추가 입력 폼·`POST /profile/complete`는 가입/Google 후속 단계다. 이번 안내 UI는 최종 오류 디자인이 아니다. 사진 API, 가족관리의 로컬 ‘나’/예시 가족 및 조건 편집의 서버 전환도 후속이며 자동 이전·삭제하지 않는다.
- 개발용 홈·스캐너 진입은 유지했다. 실서비스 프로필이 없는 개발 진입에서 임의 프로필 수정 API를 보내지 않는다.
- 검증: 단위 테스트 156개/실패 0, debug APK 및 release Kotlin 컴파일 통과. 실제 인증 서버·메일·Google 호출은 하지 않았다. New_Device 에뮬레이터 인증 내비게이션 8개 통과(오프라인 재확인/미완료 홈 차단/로그아웃/뒤로가기 포함).

## 2026-10-29 2-3단계 업데이트 — 로그아웃 통합

- 로그아웃 성공 본문은 양수 `userId`와 `serverTokenRevoked=true`를 요구한다. false/누락/손상은 서버 폐기 성공으로 처리하지 않는다. 세션 관리자가 로그아웃한 계정 ID와 응답 ID도 비교한다.
- `LogoutOutcome`으로 기기 저장 정리 여부와 서버 폐기 확인 여부를 별도로 반환한다. 토큰을 메모리/디스크에서 먼저 정리하고 캡처한 Access로 서버에 한 번 요청한다. 세션이 없으면 HTTP 요청하지 않는다.
- **만료 Access도 현재 명세의 Bearer 요청을 한 번만 시도**한다. 수용 여부가 미확정이므로 실패 시 로컬 로그아웃만 완료한 것으로 안내한다. 로그아웃을 위해 임의로 Refresh를 소비하거나 자동 재전송/재시도용 토큰을 보관하지 않는다.
- 이미 시작한 서버 요청은 화면 취소에도 HTTP 클라이언트 제한(45초) 안에서 마무리한다. 로컬 화면 전환은 서버 응답을 기다리지 않는다. 저장 정리 실패는 별도 안내하며 기기 삭제까지 성공했다고 표시하지 않는다.
- 중복 클릭은 차단하지만, 이전 계정의 로그아웃을 기다리며 새로 로그인한 계정의 로그아웃은 막지 않는다. 늦은 이전 결과가 새 세션·입력 화면·알림에 적용되지 않도록 세대와 입력 revision을 확인한다.
- 기존 로그인 선택 화면 복귀/인증 입력 초기화를 유지하고 Toast로 결과를 안내한다. 새로운 화면 디자인은 추가하지 않았다. 서버가 실패해도 홈으로 뒤로가기할 수 없다.
- 검증: **단위 테스트 134개/실패 0**, debug APK·release Kotlin 컴파일 성공. 에뮬레이터에서 `AuthNavHostTest#logoutRemovesHomeEvenIfServerUnavailable` **1개 통과**. 실제 인증 서버는 호출하지 않았다.
- **2단계에서 현재 계약으로 가능한 구현은 완료.** 만료 Access 수용/대체 절차, Refresh와 logout 경합 시 서버 폐기 보장, 실제 배포 검증은 백엔드 확인 대기다. 다음은 **3단계 GET me·앱 시작 상태 복원·프로필 PATCH**다.

## 2026-10-29 2-2단계 업데이트 — 자동 갱신 (당시 기록)

- `POST /api/auth/refresh` 연결: Body에 Refresh만 전송하고 Bearer는 붙이지 않는다. 완전한 새 로그인 응답만 허용한다. 리다이렉트와 OkHttp 자동 재전송은 금지한다.
- `AuthSessionManager`가 동시 갱신을 직렬화하고 같은 세션의 요청들이 한 결과를 공유한다. 이전 Access의 늦은 401은 이미 교체된 결과를 재사용한다. 다른 계정 또는 같은 계정의 새 로그인으로 넘어갔다면 늦은 결과를 버린다.
- 저장 포맷 v3에 `refreshPending` 추가(v1/v2 읽기 호환). 소비성 요청 전에 진행 표시를 원자 저장하고, 새 토큰 쌍 저장 성공 때만 해제한다. 진행 표시가 남은 채 프로세스가 재시작되면 이전 Refresh를 보내지 않고 재로그인한다.
- 새 Refresh는 이전 값과 달라야 하고, 동일 userId/email이어야 한다. 서버의 절대 만료를 사용하되 최초 저장 만료보다 뒤로 연장된 응답은 받아들이지 않는다. 저장 실패도 재로그인으로 처리한다.
- 갱신 시작 후 화면/요청 취소는 진행 중인 갱신의 안전한 저장 마무리를 취소하지 않는다. 실제 HTTP 클라이언트의 45초 제한 안에서 끝내고, 이미 로그아웃/계정 전환했다면 응답을 적용하지 않는다.
- `AuthenticatedRequests.execute`는 Access가 만료됐으면 전송 전에 갱신한다. 서버가 명시적으로 만료를 반환하면 갱신 후 `retrySafeRead=true`인 안전한 조회만 한 번 재전송한다. 기본값은 재전송 안 함이며, 변경 요청은 자동 반복하지 않는다. 반복 401에서도 재귀/무한 갱신하지 않는다.
- `requireCompletedProfile=false`를 명시하면 미완료/복원 세션도 me/완료용 요청을 준비할 수 있다. 갱신 성공만으로 `validatedThisRun`을 true로 바꾸지는 않는다. **GET me·앱 시작 자동 홈 복원은 3단계**다.
- 로그인 화면의 만료 감시는 이제 갱신을 호출한다. 갱신 중 홈을 유지하고, 실패 이유는 기존 로그인 오류 영역에서 안내한다. 새 디자인 화면은 추가하지 않았다.

| 갱신 결과 | 현재 프론트 처리 |
| --- | --- |
| 정상 응답 | 새 토큰 쌍 저장 후 진행 표시 해제, 현재 세션에만 반영 |
| `REFRESH_TOKEN_INVALID` / `REFRESH_TOKEN_REUSED` 401 | 로컬 세션 정리·재로그인 |
| 통신 결과 불명 / 성공 본문 손상 / 재시작 시 진행 표시 | 같은 Refresh 재사용 금지·재로그인(사용자 확정 정책) |
| 503/429/기타 서버 오류 | **임시 보수 처리:** 토큰은 진행 표시와 함께 보관하되 사용·재전송 차단, 재로그인 안내. 재시작 때도 재사용하지 않음. 서버의 오류별 소비 여부 확인 전 자동 재시도하지 않음 |
| 인증 주소 미설정 | 요청하지 않았음이 확실하므로 진행 표시만 되돌리고 저장 정보 유지 |
| 일반 보호 API의 네트워크/503/403 | 갱신·로그아웃하지 않고 기존 오류 반환 |

검증: 단위 테스트 **123개/실패 0**, debug APK·release Kotlin·Android 테스트 소스 컴파일 성공. 에뮬레이터의 실제 Keystore에서 v3 pending 저장·재시작 재로그인 테스트 **1개 통과**(격리한 테스트 키/파일). 외부 인증 서버는 호출하지 않았으며 배포 주소 검증은 남아 있다. 다음 작업은 **2-3 로그아웃·기존 흐름 통합**이다. 만료 Access의 서버 로그아웃 절차는 백엔드 확인 대기다.

## 2026-10-29 2-1단계 업데이트 — 세션 저장 (당시 기록)

- 작업 브랜치 `feature/auth-contract-models`에서 2단계를 **2-1 저장 / 2-2 자동 갱신 / 2-3 로그아웃·흐름 통합**으로 나눠 진행한다. PR #22는 사용자의 요청으로 병합 없이 닫았으며 기존 커밋은 이 브랜치에 모두 보존했다. 브랜치 삭제/새 PR 생성은 하지 않았다.
- 정책 확정: **Access 15분 + 최초 로그인부터 Refresh 30일 고정**, **갱신 응답 유실 시 재로그인**. 갱신 실패 중 재전송 가능한 오류와 만료된 Access의 서버 로그아웃 절차는 백엔드 확인 대기다.
- 저장 포맷 v2: Access/Refresh·두 만료 시각·userId/email·profileCompleted·authProvider/hasPassword를 하나의 AES-GCM 암호문으로 저장한다. Android Keystore/noBackupFilesDir를 유지한다. 비밀번호/OTP/Google 연결 증명은 저장하지 않는다.
- 서버 절대 만료를 사용하며 임의로 15분/30일을 더하지 않는다. Access-only 구형 응답만 기존 상대 시간 fallback을 허용한다. 저장 실패는 로그인 성공으로 처리하지 않는다.
- v1 파일은 Access-only로 읽고, 다음 정상 로그인 저장은 v2로 교체한다. 구형 정보에서 Refresh를 만들어내지 않는다. 손상/키 유실/미지원 버전은 인증 상태로 복원하지 않는다.
- 임시 파일 기록·동기화 후 rename으로 교체하고 저장소 read/write/clear를 직렬화한다. 교체 전 실패 시 기존 파일을 유지하며 미완성 pending 파일에서 복원하지 않는다. 로그인 저장 실패 시 세션 관리자가 전체 세션을 정리한다.
- 앱 재시작 시 유효한 Refresh를 포함한 정보는 복원하지만 GET me 검증 전 홈 진입은 허용하지 않는다. 로컬 Access 만료 시에도 유효한 Refresh를 보존하고 홈·보호 요청 자격만 중단한다.
- **자동 갱신과 서버 만료 오류 처리 전환은 2-2, 서버 로그아웃 통합은 2-3이다.** 아직 자동 로그인 30일 유지가 완성된 상태가 아니다. 기존 개발용 홈·스캐너 경로는 유지한다.
- 검증: 단위 테스트 **104개, 실패 0**; debug APK, release Kotlin 및 Android 테스트 소스 컴파일 성공. 실제 Android Keystore를 사용하는 에뮬레이터 테스트 1개도 통과했다(별도 키·파일 사용). 실제 인증 서버 호출은 하지 않았다.

## 2026-10-29 1단계 업데이트 (당시 기록)

- 후속 브랜치 `feature/auth-contract-models`, 안정적인 작업 경로는 저장소 내부 `.worktrees/auth-api-integration`이다. 기존 `/private/tmp/jjikmuk-auth-api-foundation`의 소스가 없어 Git의 인증 커밋을 복구했다.
- debug 로그인 화면의 **개발용 홈·스캐너 열기 (서버 로그인 없음)**를 복원했다. 별도 UI 경로이며 가짜 계정/토큰을 만들지 않는다. release 소스셋에는 버튼/개발 경로가 없다. 로컬 `.idea/runConfigurations/app.xml`은 Git 제외다.
- 로그인 응답에서 Refresh/만료/authProvider/hasPassword/isNewUser를 읽는다. 아직 기존 Access 저장 흐름을 사용하므로 **Refresh 저장·자동 갱신·30일 유지 구현은 다음 단계**다.
- 구형 로그인 응답에서 새 필드 묶음이 모두 없으면 Access 전용으로 명시적으로 읽는다. 일부만 있거나 모순된 응답은 InvalidResponse. Google 신규 응답 모델은 전체 새 세션 필드를 요구한다.
- Google `GOOGLE_LINK_REQUIRED`를 로그인과 구분하는 순수 디코더와 본인 Profile/PATCH 모델을 준비했다. **Google SDK/HTTP 호출·me/PATCH 호출·화면은 아직 연결하지 않았다.**
- 오류의 optional retryAfterSeconds/remainingAttempts 및 Retry-After(초/HTTP-date)를 읽는다. 잘못된 선택 필드가 있어도 유효한 code는 보존하고 서버 message/토큰은 로그에 넣지 않는다.
- 기존 OTP UI는 서버가 제공한 재전송 대기시간과 남은 시도 횟수를 사용한다. body/header가 모두 있으면 더 긴 대기를 임시로 적용하고, 둘 다 없으면 기존 60초를 사용한다. `remainingAttempts=0`이면 검증을 중지하고 재발송 안내. 필드 우선순위는 백엔드 확인 후 조정 가능하다.
- 이메일/증명 응답의 offset 시각을 epoch milliseconds로 보관한다. offset 없는 문자열에 임의 시간대를 붙이지 않는다. **정상 발송 뒤 표시용 타이머는 기존 상대 유효시간·최소 60초 로직이며**, 서버 절대 시각 기반 UI 교체는 후속이다.
- 이메일/닉네임 NFKC 정규화를 반영했다. 비밀번호는 변환하지 않고 ASCII 범위 추가 제한도 이번에 강제하지 않았다(사용자 합의 대기).
- PATCH는 필드 생략/명시적 null/문자열을 구분한다. 전용 Gson adapter로 null 해제를 보존하며 전역 serializeNulls는 켜지 않는다. 실제 Retrofit request converter를 테스트했다.
- 검증: 단위 테스트 **94개/실패 0**, debug APK, release Kotlin, Android 테스트 소스 컴파일 성공. 실서버·Google·Refresh end-to-end 검증은 아니다.

아래는 기존 기반 작업 설명이다. 새로운 계약은 [확장 API 명세](API/auth-profile-session-api.md)를 따르고, 연결 완료 여부는 위 범위를 우선한다.

이메일 로그인 화면은 실제 API와 연결했다. Google 버튼은 안내만 표시한다. 미완료 프로필은 세션을 저장하더라도 홈/일반 보호 요청에 진입하지 못하게 한다. 추가 프로필 API 확정 후 해당 화면으로 연결할 예정이다.

앱을 다시 실행하면 저장된 자격 정보를 읽되 검증 대기 상태로 둔다. `GET /api/users/me` 계약이 없으므로 저장 사실만으로 홈에 자동 진입시키지 않는다. 현재는 다시 이메일 로그인해야 하며, **30일 자동 로그인은 아직 구현하지 않았다**. 실제 로그인 응답의 수명으로만 만료를 처리한다.

## 개발 서버 설정

인증 Base URL은 제공되지 않아 기본 주소를 설정하지 않았다. 상품/OCR 주소로 자동 대체하지 않는다. 설정이 없으면 이메일을 발송했다고 표시하지 않고 서비스 이용 불가 오류로 처리한다.

디버그 앱 내부 `no_backup/auth-api.properties`에 다음 한 항목을 저장한 뒤 앱을 재시작한다.

```properties
baseUrl=https://BACKEND_AUTH_HOST/
```

- `BACKEND_AUTH_HOST`는 백엔드가 확인한 실제 인증 서버 호스트로 교체한다. 위 예시는 실행 가능한 서버가 아니다.
- HTTPS 원점 주소만 허용한다. `/api/` 접두 경로·Query·사용자명·비밀번호를 넣지 않는다.
- 토큰이나 계정 비밀번호를 이 파일에 넣지 않는다. OCR 설정 파일과 별개다.
- 예: 실제 주소만 적은 로컬 파일을 `adb push <로컬파일> /data/local/tmp/auth-api.properties`로 보낸 뒤, `adb shell run-as com.coworker.jjikmuk mkdir -p no_backup`, `adb shell run-as com.coworker.jjikmuk cp /data/local/tmp/auth-api.properties no_backup/auth-api.properties`로 복사한다. 연결 기기가 여러 대면 `adb -s <serial>`로 대상을 지정한다.
- 앱을 강제 종료 후 다시 실행하면 설정을 읽는다. 릴리스는 이 로컬 설정을 읽지 않으며, 배포 환경 설정은 추후 연결한다.
- 실제 이메일 발송/계정 변경은 서버 주소·접근 환경·테스트 계정을 확인한 뒤 수행한다. 이 작업에서는 외부 서버에 계정을 만들거나 메일을 발송하지 않았다.

## 응답 처리의 중요한 규칙

- 공개 인증 요청에 Bearer를 자동 첨부하지 않는다. 로그아웃 요청만 전달받은 서비스 토큰을 명시적으로 사용한다. OTP 증명은 Body에만 들어간다.
- 인증 클라이언트는 기존 BODY 로거와 공유하지 않는다. 자동 리다이렉트·연결 재시도와 소비성 POST의 자동 재실행을 막는다.
- `code`/`field`/선택 재시도·시도 횟수 필드와 HTTP 상태를 보존하고, 서버 message 원문을 그대로 표시하거나 로그로 남기지 않는다. 모든 401을 로그아웃으로 처리하지 않는다.
- 명확한 재전송 실패는 기존 증명을 유지한다. 응답 유실/취소/서버 5xx 등 성공 여부가 불명확하면 기존 증명을 재사용하지 않고 재발송·재인증으로 복구한다.
- 발송 제한 횟수는 서버가 판단한다. 60초 뒤에도 429가 올 수 있으며, ‘5분마다 5회’ 같은 별도 규칙을 프론트에 만들지 않았다.
- 새 서버의 offset 포함 `resendAvailableAt`을 읽도록 모델을 보완했다. 정상 발송 UI는 최소 60초를 응답 수신 이후부터 기다리며 오류 응답의 구조화된 대기시간은 반영한다. 절대 시각 기반 정상 응답 카운트다운은 후속 작업이다.
- 인증 성공 후 OTP는 소비된다. 증명은 메모리에만 두고 이메일·목적·만료를 확인한다. 프로세스가 종료되면 다시 인증한다.
- 화면을 벗어나면 화면 coroutine이 취소된다. 이메일/흐름 변경 후 도착하는 응답은 revision으로 차단한다. 타이머는 감소 횟수 대신 단조 시계의 마감 시각을 사용한다.

## 후속 작업과 계약 대기

1. 인증 서버 주소 확보 후 디버그 설정 및 실서버 발송/검증/재설정 테스트.
2. 신규 비밀번호 특수문자·기타 Unicode 허용 범위 확정. 현재 구현은 확정된 금지·필수 조건을 적용하며 임의 ASCII 전용 허용 목록은 만들지 않았다.
3. 전체 알레르기/식이조건 서버 코드 확보 후 가입 화면의 모델을 `SignUpSubmission`으로 변환. 현재 카탈로그와 서버의 snake_case/camelCase 차이를 추측하지 않는다.
4. 가입 중 사진의 업로드 시점/실패 복구를 서버 사진 계약과 함께 확정. 최종 가입은 API 없이 완료 화면으로 보내지 않으며 기존 버튼에서 이용 불가 안내를 표시한다.
5. 새로 확보한 본인 조회와 앱 시작 시 서버 검증, 30일 기준 자동 로그인/갱신 계약 연결. 세션 저장·이메일 로그인·로그아웃은 구현했으며 현재 메모리 OTP 증명과 서비스 세션은 별개다.
6. Google 명시적 계정 연결 및 추가 프로필 완료, 사진/가족 동기화는 새 명세에 맞춰 단계적으로 구현. SDK 설정·배포 정보와 미합의 정책 확인 필요.
7. 사용자가 준비할 오류 UI 반영. 이번에는 기존 입력 오류 영역/버튼/Toast를 재사용했으며 별도의 신규 오류 화면 디자인은 추가하지 않았다.
8. 분석 대상 모두 해제는 로그인 유지·개인 조건 없는 일반 조회. 상품/가족 API의 명시적 대상 없음 계약 확보 후 연결.

## 세션 구현 및 적용 경계

- `AuthSessionManager`는 저장/삭제를 직렬화하고 로그인·로그아웃·계정 전환마다 generation을 변경한다. 동일 계정으로 다시 로그인해도 이전 요청 결과는 새 세션에 반영하지 않는다.
- 로그인 성공 전에 파일 저장을 마친다. 저장 실패는 로그인 성공으로 처리하지 않는다. 취소 후 늦은 성공도 세션을 되살리지 않는다.
- 서비스 자격 정보는 암호화 파일로 저장하며 비밀번호·OTP는 저장하지 않는다. 키는 [Android Keystore](https://developer.android.com/privacy-and-security/keystore), 파일은 [백업 제외 디렉터리](https://developer.android.com/identity/data/autobackup)에 둔다.
- 로그아웃은 로컬 세션을 먼저 삭제하고 캡처한 이전 토큰으로 서버 로그아웃을 요청한다. 새 서버 계약은 현재 기기의 Access/Refresh 폐기로 변경됐다. 2-3에서 만료 Access 처리와 함께 재검증하며 새 계정의 세션을 늦은 로그아웃 응답으로 지우지 않는다.
- 비밀번호 재설정 성공 시 일치하는 이메일의 로컬 세션도 정리한다. 명확한 실패/응답 유실만으로 세션을 지우지 않는다.
- `AuthenticatedRequests.execute`는 명시적 토큰 인자를 받는 신뢰된 서비스 호출에 사용하는 기반이다. 최신 본인/프로필 API가 오면 이 경로에 연결한다. 상품·가족 조건 계약과 호스트가 미확정인 API에 공통 Bearer 인터셉터를 일괄 적용하지 않았다. OCR/상품/채팅 클라이언트에도 인증 토큰을 자동 추가하지 않는다.
- 현재 실제 보호 API 어댑터 연결은 로그아웃이다(실서버 검증 전). 로그인 API의 401/권한 403/네트워크 오류는 세션 토큰 무효로 일괄 처리하지 않는다.
- 홈 화면 상태는 세션 변경 시 폐기한다. **기존 가족·찜·기록 등 로컬 저장소의 계정별 분리/이전은 이 PR의 구현 범위가 아니다.** 기존 데이터를 임의 삭제하거나 새 계정에 귀속하지 않았다. 서버 프로필·가족 계약 및 로컬 데이터 이전 정책을 확보한 뒤 실제 다중 계정 데이터 분리를 검증해야 한다.
- 마이페이지의 비밀번호 변경/회원 탈퇴 등 서버 미연결 UI는 실제 서버 변경/탈퇴 기능으로 취급하지 않는다. 이번 PR은 인증 기반이며 전체 계정 기능의 출시 완료가 아니다.
